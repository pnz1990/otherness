SM §4b must add a `skill_citation_rate` metric: count of PRs in the last 10 batches whose description contains "Loaded skill:" divided by total PRs. Target rate: ≥60%. When `skill_citation_rate < 30%` for 10 consecutive batches: SM must open a `kind/chore priority/medium` issue: "Skills accumulating without application: N skills exist but only X% of PRs cite a skill. Skills are not being loaded. Review ENG §2c skill selection step." Without this rate, a growing skills library is unfalsifiable evidence of self-improvement — the system can point to skill count growth while never actually applying the skills. The citation rate is the bridge between "skills exist" and "agents are smarter." ⚠️ Inferred from self-improvement lens: the agents are not meaningfully smarter than two weeks ago; skills may be accumulating in `agents/skills/` without being loaded in ENG phase; no metric captures the application rate of accumulated skills.

- 🔲 Adversarial monthly review of agent instruction files — a second-opinion agent must challenge the assumptions in `standalone.md` and `phases/*.md` once per month: all self-improvement in otherness acts on the system's own outputs (PRs, metrics, learn sessions). But the agent instruction files themselves (`standalone.md`, `phases/coord.md`, `phases/qa.md`) have never been reviewed by a structurally adversarial agent. The cognitive-stance preambles (COORD=optimist, QA=skeptic) are effective within a session — but no mechanism runs an adversarial review OF the preambles themselves. SM §4c must, every 30 batches, trigger an "instruction audit" sub-session: (1) read `agents/standalone.md`, `agents/phases/coord.md`, `agents/phases/qa.md`; (2) for each section, generate 3 adversarial questions: "What assumption does this instruction make that would fail in a high-churn project?", "What does this instruction prevent that a well-functioning team would want?", "What would a team using a different methodology do here instead?"; (3) for each question whose answer reveals a structural gap: write a `🔲 Future` item in the most appropriate design doc; (4) write a PROVENANCE.md entry noting this was an instruction-file audit (not a codebase learn). Cap at 3 new Future items per audit. This is not about finding bugs — it is about finding the unquestioned assumptions the current instructions take for granted. The frame-lock problem cannot be solved by adding more instructions to the same frame; it requires a mechanism that reviews the frame itself. ⚠️ Inferred from self-improvement lens: "What would genuinely break the frame-lock?" — no existing mechanism applies adversarial review to the agent instruction files themselves; all breakout mechanisms work on outputs of the instructions, not on the instructions directly; this monthly audit is the structural intervention that operates at the correct level.

- 🔲 Learn cadence delivery enforcement — the system must guarantee at minimum 1 new skill per 28 days, tracked as a delivery obligation not a scheduling intent: the existing mechanisms (PROVENANCE.md staleness check at 14 days, skills_count hard-cap at 21 days, learn session budget reservation) are scheduling mechanisms — they trigger a learn session. But a triggered learn session that exits without a new skill file resets the clock without delivering the minimum artifact. The system currently has no binding delivery obligation: "run a learn session" and "produce a new skill" are treated as the same goal. They are not. SM §4c must track `skills_last_new_file_date` — the git modification date of the newest `agents/skills/*.md` file excluding `README.md` and `PROVENANCE.md`. If `skills_last_new_file_date` is more than 28 days ago: SM §4c must open a `priority/critical` issue regardless of PROVENANCE.md date or open learn issues: "[DELIVERY FAILURE] No new skill file in 28 days. Learn sessions may be running but not producing artifacts. This is a self-improvement delivery failure, not a scheduling gap." This hard cap on 28-day delivery makes the obligation concrete and unfakeable: PROVENANCE.md updates cannot satisfy it, only a new `agents/skills/*.md` file can. Without this delivery gate, the self-improvement loop can appear healthy (learn sessions triggered, PROVENANCE.md updated) while producing no compounding knowledge for months. ⚠️ Inferred from self-improvement lens: "/otherness.learn runs rarely" is the symptom; "when it runs it produces no skill" is a deeper failure; the delivery enforcement gate closes the gap between "learning was scheduled" and "learning actually compounded."
