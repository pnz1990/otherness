- 🔲 Frame-lock break protocol as a scheduled mechanism, not a human-triggered event: the current pattern for frame-lock is: simulation detects arch_convergence > 0.7 → opens `[NEEDS HUMAN]` issue → human runs `/otherness.learn`. The human is the executor. But the point of frame-lock detection is to break the loop autonomously. SM §4c must implement an auto-escalation path: if arch_convergence > 0.7 AND the last autonomous learn session is >14 days ago AND no human has responded to the `[NEEDS HUMAN]` issue in >48 hours: SM §4c automatically triggers a learn session (same as the normal learn trigger, but with `paradigm_diversity_required: true` flag). The human issue stays open as a notification. This converts frame-lock from "human must notice and act" to "system detects and heals, human informed." ⚠️ Inferred from self-improvement lens: monoculture break currently requires human initiation; the system cannot break its own frame-lock without human intervention.
- 🔲 Phase-role cognitive diversity — COORD, ENG, QA, SM must each frame problems from a genuinely different perspective: all four phases run through `standalone.md` and therefore share the same reasoning framework. When COORD generates work, ENG implements it, and QA reviews it, all three use the same frame — so QA cannot truly challenge what ENG built because they start from the same mental model. This is a deeper problem than skill monoculture: it is structural. Each phase must be given an explicit cognitive stance that is designed to conflict with the others. COORD: optimistic incrementalist (what can be shipped quickly?). ENG: pragmatic builder (what is the minimal change that is correct?). QA: adversarial skeptic (what assumption is wrong here?). SM: historian (what pattern do we keep repeating?). These stances should be injected as phase-header preambles in each `phases/*.md` file. A QA phase that has been explicitly told "your job is to find the assumption this PR got wrong" will reject PRs that a same-framed QA would approve. ⚠️ Inferred from self-improvement lens: monoculture — all phases share the same reasoning framework; the QA adversarial review is nominal because QA is not structurally opposed to ENG.
- 🔲 Skill load verification: ENG must confirm which skills were loaded before implementation — skills accumulate in `agents/skills/` but there is no mechanism verifying the ENG phase actually loaded the relevant one before starting work. A skill that exists but is never loaded has zero impact. ENG `§2c` must: (a) list the skill files checked at session start, (b) select the most applicable skill file for the current item type, (c) log "Loaded skill: `<filename>`" in the PR description. SM §4b must check that the last 5 ENG PRs each include a "Loaded skill" line — if fewer than 3 of 5 do, SM opens a `kind/chore` issue: "Skill loading discipline has drifted — ENG is not citing skill files." Without this check, skill accumulation is fiction. ⚠️ Inferred from self-improvement lens: skills grow but agents may not be loading them; no verification loop confirms skills are applied.

Two session delays before learning happens. When COORD §1b detects at session start that PROVENANCE.md is >14 days stale AND no open learn issue exists AND no active learn branch exists: COORD must immediately create the learn issue and claim it in the same session — the current session becomes a learn session. The human never needed to initiate it. The SM detection path should remain as a fallback for when COORD misses the condition, but COORD acting first collapses two session delays to zero. ⚠️ Inferred from self-improvement lens: /otherness.learn runs rarely because it waits for SM to detect the condition, which waits for COORD to observe the issue, which waits for a session to claim it — three separate sessions before learning occurs.

Without the field in PROVENANCE.md, SM §4c cannot implement the diversity check regardless of how the instruction is written — it is a spec without an artifact. The monoculture breakout mechanism cannot work until PROVENANCE.md carries the paradigm metadata SM needs to enforce diversity. ⚠️ Inferred from self-improvement lens: the monoculture problem has not been addressed; the paradigm_category tracking mechanism is specified but the PROVENANCE.md format does not include the required field, making the diversity enforcement unimplementable in practice.
- 🔲 QA adversarial rejection rate tracked as a first-class self-improvement metric: the phase-role cognitive diversity item (above) specifies that QA must act as an "adversarial skeptic" — but there is no metric that confirms QA is actually rejecting PRs at a rate consistent with genuine adversarial review. A QA phase that approves every PR is not adversarial; it is a rubber stamp. SM §4b must track `qa_rejection_rate`: the ratio of PRs that QA rejected or requested changes on vs. total PRs reviewed in the last 20 batches. A `qa_rejection_rate` of 0% for 10 consecutive batches is strong evidence that QA is not applying adversarial review — it is approving everything ENG produces. When `qa_rejection_rate == 0` for 10 batches: SM §4c must open a `kind/chore priority/high` issue: "QA rejection rate is 0% over 10 batches — QA is not functioning as an adversarial reviewer. Phase-role cognitive diversity preambles may not be loaded, or QA stance instruction needs strengthening." A system that claims to have adversarial QA must be able to prove it with a non-zero rejection rate. ⚠️ Inferred from self-improvement lens: the QA adversarial review is nominal because QA is not structurally opposed to ENG; there is no metric confirming QA ever rejects anything, making the adversarial claim unverifiable.
- 🔲 `/otherness.learn` must target codebases that solve genuinely DIFFERENT problems than otherness itself: every learn session picks a "high-signal open-source repo" — but the selection heuristic is unspecified. In practice, the agent likely gravitates toward well-maintained, well-documented repos that share properties with otherness (configuration-driven, automation-oriented, markdown-heavy). This is monoculture by selection: the learning corpus reinforces the same paradigm. `/otherness.learn §1b` must add a diversity gate: before committing to a target repo, the agent must: (1) read the last 3 PROVENANCE.md entries for the `paradigm_category` field; (2) if the candidate repo falls in the same category as the last 2 sessions (or has no category precedent): select a different repo from a pre-seeded list of paradigm-diverse candidates (e.g. a Haskell/Elm functional project, an Erlang actor-model project, a Kubernetes operator for declarative config, a reactive streams library). The pre-seeded list is maintained in `agents/skills/README.md` under a `## Learning Target Diversity Pool` section. Without this gate, `/otherness.learn` is a repetitive process that generates skills within the same reasoning frame. ⚠️ Inferred from self-improvement lens: /otherness.learn runs rarely; when it does run, it likely selects paradigm-similar targets because the selection heuristic is undefined — resulting in learning that reinforces the existing monoculture.
- 🔲 Phase preamble injection verification: the phase-role cognitive diversity item specifies that COORD, ENG, QA, and SM must each be given a cognitive-stance preamble (optimistic incrementalist, pragmatic builder, adversarial skeptic, historian). But the phases are in `agents/phases/*.md` — a CRITICAL tier file that requires human review before merge. The implementation spec is defined in this doc but the actual preamble injection can only land via a CRITICAL tier PR. To avoid blocking indefinitely on human review: (1) the preambles should be designed as ADD-ONLY instructions (not rewrites of existing phase content) so the CRITICAL tier risk is minimal; (2) scripts/validate.sh should add a check: for each phase file, verify it contains a "Cognitive stance:" line within the first 50 lines — if absent, emit a warning (not an error, to avoid blocking non-phase PRs). This converts an indefinitely-deferred spec into an observable gap: every validate.sh run surfaces which phases are missing their cognitive preamble. ⚠️ Inferred from self-improvement lens: the monoculture problem has not been addressed; the phase-role cognitive diversity spec exists but the implementation requires CRITICAL tier changes that may sit in review indefinitely without a progress signal.
- 🔲 `agents/skills/README.md` must list "when NOT to load this skill" for each skill: the skill index currently describes when to load each skill — but skills can also cause harm when loaded in the wrong context (a contribution-hygiene skill loaded during a hotfix increases overhead; an architectural-audit skill loaded during a routine docs PR is scope creep). Each skill entry in `agents/skills/README.md` must include a "When NOT to load:" line. ENG §2c skill selection must filter out skills marked "not applicable to this item type". This is the negative space of skill loading: the system is not smarter if it loads every skill for every item. Over-loading slows sessions and introduces irrelevant constraints. The absence of "not applicable" guidance is a skill system design gap. ⚠️ Inferred from self-improvement lens: skills accumulate but agents may be loading inappropriate skills for given item types; no guidance exists for when a skill should explicitly NOT be applied.
- 🔲 Cross-session learning capture: skills learned in one session are written to `agents/skills/` — but intermediate observations that don't rise to "skill" quality are discarded. An observation like "GitHub API rate limits at 100 calls/min for search; use `--limit 50` to avoid silent truncation" is not a skill but is a transferable lesson. These micro-observations currently live only in session context and are lost when the session ends. SM §4f must maintain a `agents/skills/micro-observations.md` file — a rolling list of <20 factual observations from recent sessions that don't meet the full skill quality bar. The file is capped at 20 entries (oldest removed when new ones arrive). ENG §2c loads this file as "ambient context" (not a formal skill) at session start. Without this capture, sessions repeatedly learn the same practical lessons (API rate limits, git worktree edge cases, gh CLI quoting rules) without that knowledge compounding. ⚠️ Inferred from self-improvement lens: the agents are not meaningfully smarter than two weeks ago because valuable sub-skill observations are discarded between sessions; the skill quality gate is too high for practical lessons.
- 🔲 Hard cap on maximum time between learn sessions — 21-day unconditional trigger: the existing PROVENANCE.md staleness check fires when the last entry is >14 days old — but this check can be fooled. A learn session that opens a PR, touches PROVENANCE.md without extracting a real skill, and closes cleanly will reset the 14-day clock without learning anything. The result: the cadence check always sees PROVENANCE.md as "recent" while no genuine learning has occurred for months. SM §4c must add a second, independent trigger: count the total number of skill files in `agents/skills/` at the start of each SM cycle; compare to the count from 21 days ago (stored in `state.json` as `skills_count_21d_ago`). If `skills_count` has not increased in 21 days: SM §4c must open a `priority/critical` learn issue regardless of PROVENANCE.md date: "[HARD-CAP] skills_count unchanged for 21 days — learning has not produced a new skill file in 3 weeks. PROVENANCE.md date check insufficient. Forcing learn session." The distinction: PROVENANCE.md checks that learning was attempted; skills_count checks that learning actually produced an artifact. Both checks must pass before the cadence is considered healthy. Without the skills_count hard cap, the learn cadence can appear healthy (PROVENANCE.md fresh) while the skill library is genuinely frozen. ⚠️ Inferred from self-improvement lens: /otherness.learn runs rarely; even when it runs, the PROVENANCE.md staleness gate can be satisfied without extracting a new skill; there is no mechanism enforcing that skill growth actually occurs on a bounded schedule.
- 🔲 `/otherness.learn` runs rarely because COORD does not budget for it — session budget allocation root cause: every batch, COORD picks from the queue based on priority/size/kind. A `learn(arch):` issue competes with `kind/enhancement priority/high` feature items — and it always loses because the queue richness guard (doc 22) explicitly prioritizes feature items. A learn session takes a full session's budget (it uses OpenCode's full context doing repo analysis + skill writing + PR review). COORD §1e claim logic currently treats a learn issue the same as a normal feature issue — same sort key, same budget model. The root cause is that COORD has no concept of a "full-session task" vs. a "normal task". When a learn issue is at the top of the queue: COORD must reserve the ENTIRE session budget for it (not attempt other items after), commit to the learn session explicitly, and not allow the queue richness guard to steal priority from it. Additionally, when claiming a learn issue, COORD must log "SESSION TYPE: learn — no other items will be claimed this session." Without this budget reservation, a learn issue gets claimed, partial work starts, the session context fills up, and the session exits with PROVENANCE.md untouched. The learn cadence check then sees an "in-progress" branch and waits — adding a 1-session delay. The result: /otherness.learn runs rarely because the session budget model treats deep research tasks the same as incremental implementation tasks, and the queue priority system consistently starves the former in favor of the latter. ⚠️ Inferred from self-improvement lens: /otherness.learn runs rarely; the agents are not meaningfully smarter than two weeks ago; the root cause is not detection or scheduling but session budget allocation — learn issues compete against feature items and lose every time.
- 🔲 External paradigm challenge — invite a structurally different approach to critique the current loop design: all self-improvement in otherness is internal: agents review their own outputs, skills are extracted from sessions the same agents ran, and the frame-lock problem is addressed by adding more instructions to the same agents. This is recursive improvement within the same ontology — it cannot produce a genuinely different perspective. A structural break requires an external viewpoint. `/otherness.learn` must add a step: once every 10 learn sessions (tracked via `PROVENANCE.md` entry count in the `learn_count_mod_10` field), instead of learning from a codebase, the learn session must: (1) read the current `agents/standalone.md`, `agents/phases/coord.md`, `agents/phases/qa.md`; (2) formulate 5 specific critique questions about the architecture (e.g. "What assumption does this loop make that would be false in an event-driven system?", "What would this loop do differently if it prioritized reversibility over throughput?"); (3) answer each question from first principles, without reference to existing design docs; (4) compare answers to what the existing design docs say; (5) for each divergence found: write a `🔲 Future` item in `docs/design/` or a new `agents/skills/` entry. This is not about finding bugs — it is about finding paradigm assumptions the current design takes for granted. Without this step, the learn sessions optimize within the existing frame. The frame itself cannot be critiqued by an agent running inside it. ⚠️ Inferred from self-improvement lens: "What would genuinely break the frame-lock?" is explicitly raised by the pressure context but no design doc specifies a mechanism for generating critiques that are genuinely outside the current reasoning frame; all existing mechanisms (cognitive preambles, paradigm-diverse codebases) are improvements to the same loop, not challenges to the loop's foundational assumptions.
- 🔲 LLM temperature and model diversity as a structural frame-lock break: the monoculture problem identified in doc 10 and in the simulation is attacked via cognitive-stance preambles (COORD=optimist, QA=skeptic) and paradigm-diverse learning targets — but all phases still run at the same model, the same temperature, and the same system prompt structure. The QA adversarial stance preamble cannot fundamentally challenge ENG's output if QA runs on the same weights, the same context window, and the same generation temperature as ENG. To genuinely break frame-lock, the QA phase must run at elevated temperature (higher randomness → more likely to surface unexpected objections) while ENG runs at lower temperature (more deterministic implementation). Additionally, when `arch_convergence > 0.7`: SM §4c must set a `use_high_temp_qa: true` flag in state.json; the standalone.md QA phase must pass this flag to the underlying OpenCode invocation (via `OPENCODE_TEMPERATURE` env var or equivalent mechanism). This is the one structural change that cannot be replicated by instruction text alone — it requires a parameter change at the model invocation level. Without it, cognitive-stance preambles are a nudge; temperature diversity is a genuine constraint. Research basis: adversarial evaluation is more effective when the evaluator has higher stochasticity than the generator (diverse sampling surfaces more edge cases). ⚠️ Inferred from self-improvement lens: monoculture — all agents share the same reasoning framework — has not been addressed at the model-parameter level; cognitive preambles address framing but not sampling diversity; the most reliable way to break frame-lock is to make QA structurally different from ENG at the generation level.

- 🔲 Monoculture breakout verification — arch_convergence must measurably decrease after a paradigm-diverse learn session: the existing frame-lock mechanism (SM §4c opens `learn(arch):` issue when arch_convergence > 0.7) defines the trigger but not the success criterion. A learn session runs, PROVENANCE.md is updated, `frame_lock_detected` is cleared in `state.json` — but there is no step that verifies arch_convergence actually decreased in the subsequent calibration. The frame-lock flag is cleared based on "a learn session ran" not on "arch_convergence dropped." This is the measurement gap: the breakout mechanism has no feedback loop confirming it worked. SM §4e-iii simulation-behavior coupling gate verifies that the `trigger_learn` recovery action led to a learn session being opened — but it does NOT verify that the post-learn calibration shows reduced convergence. SM §4e must add a post-learn convergence check: (1) after each calibration following a learn session (detected by comparing current `calibrated_at` to last PROVENANCE.md date), compare new `arch_convergence_score` to the pre-learn score (stored as `pre_learn_arch_convergence` in `sim-prediction.json`); (2) if arch_convergence did NOT decrease by ≥0.1 after the learn: open a `kind/chore priority/high` issue: "Frame-lock breakout verification FAILED — arch_convergence was {pre} before learn, {post} after. The paradigm-diverse learn session did not reduce architectural convergence. Root cause: either the learned paradigm was too similar to existing skills, or the skill was not loaded in ENG phase"; (3) clear `frame_lock_detected` ONLY when convergence drops by ≥0.1 — not when a learn session runs. A system that can detect frame-lock but cannot verify whether its breakout attempt succeeded has a one-way ratchet: it knows when it is stuck but never knows if it got unstuck. ⚠️ Inferred from self-improvement lens: the agents are not measurably smarter; the monoculture problem has not been addressed because the breakout mechanism has no success criterion and no verification that arch_convergence actually improves post-learn.
- 🔲 skills_count and PROVENANCE.md last-learn date must be published in the SM health comment every batch: the health comment currently shows batch number, health signal, meaningful PRs, and queue depth. It does NOT show `skills_count` or when the last learn session completed. A human looking at the health comment cannot tell if the skills library is growing or frozen. SM §4f must add two fields to the health comment: "Skills: N (last learn: YYYY-MM-DD)" and color-code the learn date: green if <14 days, amber if 14-30 days, red if >30 days. The `skills_count` should also flag stagnation: if `skills_count` is the same as the value from 20 batches ago (readable from `metrics.md`), show "Skills: N (⚠️ unchanged 20+ batches)". These two fields transform the health comment from a delivery signal into a learning signal — the human sees at a glance whether the system is getting smarter or just shipping. Without these fields, the self-improvement loop is invisible in the health signal, and the human must manually read PROVENANCE.md and count skill files to know if learning is happening. ⚠️ Inferred from self-improvement lens: the skills library grows slowly; no mechanism surfaces the rate of skill growth in the primary health signal where a human would notice it.
- 🔲 Learn session skill-extraction success rate must be a tracked metric, not just a count: `docs/aide/metrics.md` tracks `skills_count` (total skill files), but this metric cannot distinguish "we ran 5 learn sessions and each produced 1 skill" from "we ran 5 learn sessions and 4 of them updated PROVENANCE.md without adding a new skill file." The success rate of learn sessions (sessions that produce a new `agents/skills/*.md` file vs. sessions that close without one) is the actual measure of whether learning is working. SM §4b must track `learn_sessions_run` and `learn_sessions_with_new_skill` as columns in `metrics.md` — updated whenever PROVENANCE.md is modified. `learn_session_success_rate = learn_sessions_with_new_skill / learn_sessions_run`. PM §5 stagnation check must flag when `learn_session_success_rate < 50%` over the last 5 sessions: this means the learning process is running but failing to extract skills more often than it succeeds. A system whose learn sessions succeed less than half the time is not self-improving — it is burning session budget on learning that does not compound. Without this rate, a flat `skills_count` over 20 batches looks the same as "no learn sessions ran" and "5 learn sessions ran but extracted nothing" — the root causes are completely different and require different fixes. ⚠️ Inferred from self-improvement lens: the agents are not meaningfully smarter than two weeks ago; the current metrics track whether learning was attempted but not whether it succeeded; a 0% learn success rate and a 100% success rate both appear identical in the current schema.
- 🔲 Frame-lock status must be visible in the health comment on every batch, not just when triggered: `frame_lock_detected` is written to `state.json` when arch_convergence exceeds the threshold and cleared when it drops. But the health comment only mentions frame-lock when a `[NEEDS HUMAN]` issue is opened — which itself only happens when the threshold is exceeded for 2 consecutive calibrations. Between calibrations (every 10 batches), `frame_lock_detected` can be `true` in `state.json` while every health comment says GREEN with no mention of frame-lock. A human reading the health comment 8 batches after frame-lock was set sees no indication the system is in a monoculture state. SM §4f must include a one-line frame-lock field in the health comment every batch: "Frame-lock: CLEAR (convergence: 0.42)" or "Frame-lock: DETECTED (convergence: 0.78 — learn session pending)". When `frame_lock_detected=true`: health signal must be AMBER at minimum, regardless of other signals. The frame-lock condition means the system's reasoning is converging — a session that runs in frame-lock state is making the monoculture worse, not better. GREEN while frame-locked is dishonest. ⚠️ Inferred from self-improvement lens: the monoculture problem has not been addressed; the current design detects frame-lock but does not propagate the detection to the health signal or the health comment between calibration cycles, making the condition invisible to the human for up to 10 batches after detection.
