## Future (🔲)

### Lens 1 — Reliability: sessions fail silently, produce housekeeping-only PRs

- 🔲 46.1 — GitHub Actions concurrency collision must be detected and surfaced — two scheduled runs overlapping produce a ghost session that consumes capacity but ships nothing: `otherness-scheduled.yml` does not set a `concurrency:` group. When the cron fires every hour and a previous run is still in progress (ENG phase running a long build), GitHub queues or cancels the new run depending on the cancel-in-progress setting. If cancel-in-progress is false (default), two sessions run simultaneously — both read the same `_state`, both claim different items, and the second session may try to push to a `feat/` branch that already exists. If cancel-in-progress is true, the queued run is cancelled silently and the human sees a grey ✗ in the Actions tab with no explanation of why. Neither case is detected by any existing mechanism. `otherness-scheduled.yml` must add `concurrency: group: otherness-${{ github.repository }} cancel-in-progress: false`. When cancel-in-progress is false AND a run is queued, GitHub waits — the queued run inherits the `_state` after the first run completes, which is correct behaviour. SM §4a must also check: if the last `_state` commit shows two different session branches both moving to `in_progress` within 30 minutes of each other (detectable by `gh api repos/$REPO/commits?sha=_state`), flag `concurrent_session_detected: true` in state.json and post to the report issue. Without the concurrency group, the scheduled workflow has a race condition on every near-miss hourly trigger that is undetectable and produces ghost sessions. ⚠️ Inferred from reliability lens: sessions fail silently; one specific cause — concurrent workflow runs — has no current detection or prevention mechanism despite being configurable in 2 lines of YAML.

- 🔲 46.2 — ENG worktree cleanup must be guaranteed before each new claim — leftover directories from aborted sessions cause silent ENG failures: COORD §1e creates a git worktree via `git worktree add ../feat-<item>-<hash> -b feat/<item>`. If the previous session that claimed this item aborted mid-execution (OOM kill, runner timeout, network loss), the worktree directory `../feat-<item>-<hash>` may still exist on disk with uncommitted changes. The next session that attempts to re-claim the same item (after the stale watchdog reclaims it) runs `git worktree add` again — which fails with "fatal: already locked" or "fatal: '<path>' already exists". ENG never starts. The item returns to `todo`. The stale watchdog fires again 60 minutes later. This cycle can repeat indefinitely. COORD §1e must add a pre-claim cleanup step: before creating a new worktree, run `git worktree prune --expire=now` to remove stale worktree registrations, then check if the target path exists: `if [ -d "../feat-<item>-<hash>" ]; then rm -rf "../feat-<item>-<hash>"; fi`. Additionally, SM §4a stale-branch watchdog must, when reclaiming an item, clean up the worktree on the runner's filesystem (via a `git worktree remove --force <path>` step). Without this cleanup, a single aborted ENG session creates a persistent worktree lock that silently blocks all future attempts to work on the same item. ⚠️ Inferred from reliability lens: sessions fail silently; the worktree cleanup gap is a known failure mode mentioned in the Stage 1 deliverables but has no `🔲 Future` item specifying the exact cleanup sequence.

- 🔲 46.3 — `[NEEDS HUMAN]` deduplication must be enforced across concurrent sessions — parallel sessions can both post `[NEEDS HUMAN]` for the same root cause: when two sessions run close together (hourly cron + a manual `/otherness.run`), both sessions may detect the same condition (e.g. CI has been red for 25 hours) and both open a `[NEEDS HUMAN: ci-blocked]` issue. The operator receives two identical `[NEEDS HUMAN]` issues with slightly different timestamps. The deduplication check in SM §4b looks for an existing open issue with a matching title before creating a new one — but if both sessions run the check within seconds of each other (before either has created the issue), the race window allows both to pass the "no open issue" check and both create the issue. COORD §1b-preflight reads `needs_human_count` — but from `_state`, which is updated at the END of the session, not at the start. SM §4b must use a GitHub API search as its deduplication gate (not `_state`), and the search must include an exact-match on the title prefix before creating: `gh issue list --search "[NEEDS HUMAN" --state open --json title | python3 -c "..."`. Any open `[NEEDS HUMAN]` issue that matches the first 60 chars of the proposed title must prevent creation. This is already the nominal design — this item specifies that the implementation must query the GitHub API (not `_state`) to close the race window. ⚠️ Inferred from reliability lens: a truly reliable system should not generate duplicate escalations; duplicate `[NEEDS HUMAN]` issues create confusion and erode operator trust in the signal.

### Lens 2 — Honesty: SM says GREEN but products not advancing, simulation decorative

- 🔲 46.4 — Simulation `arch_convergence` score must appear in every SM health comment, not only at calibration time — the gap between calibrations leaves the operator blind for up to 10 batches: SM §4e computes `arch_convergence` every 10 batches and writes it to `sim-prediction.json`. SM §4f posts the health comment every batch. But `arch_convergence` is not included in the per-batch health comment — only in the calibration-run comment posted by SM §4e. A human reading the last 9 health comments after a calibration has no visibility into the arch_convergence score. 45.2 adds a simulation action trace — but that trace is only posted at calibration time. SM §4f must read `arch_convergence` from `_state:sim-prediction.json` every batch and include it as a one-line field in the health comment: "Convergence: 0.42 (calibrated: 5 batches ago)". When `arch_convergence > 0.7`: show "Convergence: ⚠️ 0.78 (frame-lock zone — learn pending)". The age annotation ("5 batches ago") tells the human whether the value is fresh or stale. Without this field, arch_convergence is computed every 10 batches but invisible for 9 of them — the health comment omits the system's own self-model of monoculture risk. ⚠️ Inferred from honesty lens: the simulation exists but its predictions are not visibly changing agent behavior every session; "every session" requires the simulation output to be present in every health comment, not just every 10th.

- 🔲 46.5 — `docs/aide/metrics.md` schema drift must be detected before it causes silent column-count errors — new columns added by agents break Python row-parsing in SM: `docs/aide/metrics.md` has a defined header row. SM §4b writes new data rows matching this header. But when a feature PR adds a new column (e.g. `qa_rejection_rate`) by updating the header and writing the new column in the current row, all prior rows in the file have N columns while the header now has N+1. Python code that reads metrics.md by column index (`row.split('|')[7]`) silently reads the wrong column for old rows and IndexError-crashes for new rows that expected the column to exist. SM §4b must: (1) validate the header row against a local constant in its Python block before writing any new row; (2) if a column is added: backfill all prior rows with an empty string for the new column as part of the same commit; (3) if the actual row count does not match the header column count on read: log "⚠️ metrics.md schema drift detected: header has N cols, row M has K cols" and fail-open (skip the row, continue). `scripts/validate.sh` must add a check: parse the header column count and verify all non-header rows have the same count (python3 one-liner). Without this check, any PR that adds a metrics column breaks all future metrics reads silently — SM reads wrong data, computes wrong health signals, and opens issues based on corrupted metrics. ⚠️ Inferred from honesty lens: metrics are being collected but the schema-drift gap means collected metrics can become silently wrong after any column-add PR; this is an undetected corruption path.

- 🔲 46.6 — "No-ops passing as work" detection — SM must detect when a PR was merged but changed 0 lines outside docs/aide/ and does not move a `🔲 → ✅` item: the `meaningful_prs` filter (doc 35, SM §4b) already excludes housekeeping-only PRs whose ALL changed files are in `docs/aide/`. But a PR can change 1 line in `agents/phases/sm.md` (adding a blank line or adjusting a comment) while claiming to implement a design doc item — this PR passes the "real code" filter (`docs/aide/` exclusion) but delivers no behavioral change. This is the "no-op PR" problem: the PR count goes up, `meaningful_prs` ticks up, health says GREEN, but nothing actually changed. SM §4b must add a `net_behavioral_change` heuristic to the meaningful-PR filter: a PR is meaningful only if it changes ≥5 net lines in agent/phase/script files (excluding comments and blank lines). The threshold is low (5 lines) to avoid false negatives on genuine one-line fixes, but it excludes formatting-only or comment-only PRs that change nothing behavioral. `gh pr view $PR_NUMBER --json additions,deletions` gives the raw counts; subtract comment lines (lines starting with `#` or `> `) from the additions count. If `net_additions < 5` AND no `🔲 → ✅` transition in the PR body: flag the PR as non-meaningful. ⚠️ Inferred from honesty lens: the loop is not honest enough; the SM health signal counts meaningful PRs but the current definition allows comment-only or whitespace-only changes to count as meaningful work; a stricter behavioral-change filter closes this honesty gap.

### Lens 3 — Self-improvement: skills grow slowly, monoculture unaddressed, agents not smarter

- 🔲 46.7 — `/otherness.learn` pre-scan heuristic must identify a target repo's paradigm category before committing to it — the paradigm category field in PROVENANCE.md must be set from a real assessment, not guessed post-hoc: `agents/otherness.learn.md` and SM §4c specify that learn sessions target repos from diverse paradigm categories (functional, event-sourced, actor-model, etc.) and that PROVENANCE.md entries include a `paradigm_category:` field. But no step in the current learn flow actually assesses the target repo's paradigm BEFORE the session commits to learning from it. The learn session reads the codebase and writes PROVENANCE.md with whatever category seems appropriate after the fact — this is post-hoc labeling, not pre-scan filtering. Two problems: (1) the SM §4c diversity check can't prevent same-paradigm back-to-back sessions if the paradigm isn't known until AFTER the session runs; (2) a learn session can "assess" the paradigm incorrectly (labeling a TypeScript REST API as "functional" because it uses `.map()`) without any challenge. `agents/otherness.learn.md` must add a STEP 0 pre-scan: (a) run `gh repo view <target> --json description,topics,primaryLanguage` to get the repo metadata; (b) read the first 50 lines of the primary source file; (c) assess the paradigm from these signals before reading the full codebase; (d) if the assessed paradigm matches the last PROVENANCE.md entry's category: STOP and select a different target repo. Only commit to learning from a repo after the paradigm pre-assessment passes the diversity check. This makes diversity enforcement pre-emptive (before spending session budget) rather than reactive (detecting repetition after the session runs). ⚠️ Inferred from self-improvement lens: the monoculture problem has not been addressed because paradigm categories are labeled post-hoc; the pre-scan heuristic is the missing step that makes the diversity mechanism enforceable before session budget is spent.

- 🔲 46.8 — Contradictory skills must be detected and resolved — the skills library can accumulate conflicting advice as it grows: `agents/skills/` currently has 12 files. As the library grows toward 20–30 skills, the probability of contradiction increases: a skill added in batch 5 may recommend "always open a tracking issue before starting work" while a skill added in batch 80 (after the COORD preflight was redesigned) recommends "use state.json directive instead of opening issues for session steering." Both are in `agents/skills/README.md`. ENG loads both. The ENG phase receives contradictory instructions and the LLM must resolve the contradiction implicitly — without any guidance on which advice takes precedence. SM §4b must, every 20 batches, run a skill-contradiction check: for each pair of skill files loaded in the last 5 ENG sessions (from PR description "Loaded skill:" lines), detect textual contradictions (sentences that recommend opposite actions on the same trigger condition). The heuristic: if skill A contains "always X when Y" and skill B contains "never X" or "avoid X": flag the pair as potentially contradictory. Open a `kind/chore priority/medium` issue: "Skill contradiction detected: `<fileA>` and `<fileB>` may give conflicting instructions on [topic]. Review and reconcile." Without this check, the skills library becomes an accumulating source of inconsistent advice — and ENG, which "loads the most applicable skill", will silently pick one and ignore the other, making the un-picked skill dead weight. ⚠️ Inferred from self-improvement lens: the agents are not meaningfully smarter because accumulated skills may be contradicting each other; no mechanism detects when two skills provide conflicting advice on the same trigger condition.

- 🔲 46.9 — Inter-session knowledge continuity via session-closing knowledge dump — skills lost between sessions because the extraction threshold is too high: the skill quality gate (specific, falsifiable, novel, transferable) correctly prevents low-quality skills from entering the library. But between session end and the next session start, ALL reasoning built up during the session is lost — including valid intermediate insights that did not rise to full "skill" quality. This is not about micro-observations (covered in doc 31, 31.42) but specifically about the session's final reasoning state: what did the agent learn about the codebase, about the failure mode it just fixed, and about the interaction patterns it observed? ENG §2f (PR opening) must add a "Session reasoning dump" step: after the PR is opened and before SM/PM start, ENG must write a 5-bullet "What I learned this session" note to `agents/skills/session-notes.md` (a rolling file, max 10 entries, LIFO). COORD §1b-preflight must read this file at session start as "prior session context." This is not the micro-observations file (doc 31) — it is specifically the reasoning about the JUST-COMPLETED implementation that the next session's COORD would benefit from knowing (e.g., "The GitHub Actions workflow concurrency issue required adding a `group:` key — check for this pattern in other workflow files."). Without this dump, each session starts cold on a warm problem — the next session that touches the same area rebuilds context from scratch. ⚠️ Inferred from self-improvement lens: the agents are not meaningfully smarter because session-local reasoning is completely discarded; the skills extraction gate is high; session notes are a lower-cost continuity mechanism that doesn't require full skill quality.

### Lens 4 — Onboarding: new projects still require human intervention

- 🔲 46.10 — `otherness-config.yaml` `monitor.projects` list must be validated as reachable repos at onboarding time — projects added to the monitor list that the bot cannot access are silently ignored: `PM §5 Scenario 1` reads `monitor.projects` from `otherness-config.yaml` and checks each project's `_state` branch. But if a project is listed that (a) does not exist, (b) is private and the `GH_TOKEN` has no access, or (c) was renamed/transferred, the `gh api` call returns 404 and PM §5 silently skips it (fail-open behaviour). The operator may believe the project is being monitored when it is not. `/otherness.onboard` STEP 7 must, when adding a new project to `monitor.projects`, run a reachability check: `gh api repos/<owner>/<repo>/branches/_state --jq .name 2>&1`. If the result is not `"_state"`: warn the operator: "⚠️ Added `<repo>` to monitor.projects but its `_state` branch is not reachable with current credentials. The project will be monitored but PM §5 checks will silently skip it until access is confirmed." Additionally, PM §5 Scenario 1 must log when it skips a project due to API error: "⚠️ monitor.projects: `<repo>` unreachable (HTTP 404/403) — check credentials." Without these warnings, the monitor list can silently degrade to 0 reachable projects while appearing to have 3 entries. ⚠️ Inferred from onboarding lens: a new project added today would still require significant human intervention; the monitor list is how the operator confirms the system is watching managed projects; silent unreachability leaves the operator with false confidence in the monitor coverage.

- 🔲 46.11 — Post-onboarding health verification command must be runnable without local credentials — new operators should be able to verify onboarding success from the GitHub UI: the current onboarding verification step requires running `scripts/check-onboarding.sh` locally, which requires a working `gh` CLI authenticated to the target repo. A new operator who has just cloned the repo and is in the process of setting up secrets may not have local credentials yet. The verification command fails with "gh: not authenticated" — precisely when they most need it to work. `/otherness.setup` must add a "GitHub-only verification" path: a set of `gh` API commands that can be run from ANY authenticated GitHub environment (GitHub CLI in Codespaces, a CI job, or the GitHub web UI's Actions `workflow_dispatch` trigger). Specifically, a `scripts/verify-onboarding.sh` script that checks the 5 most common onboarding gaps using only `gh` API calls and prints PASS/FAIL for each: (1) `_state` branch exists, (2) report issue exists and is open, (3) scheduled workflow is enabled, (4) required secrets are present (by checking secret NAMES, not values — `gh secret list`), (5) `otherness-config.yaml` has non-empty `schedule.cron`. This script can be run as a `workflow_dispatch` step — the operator triggers it from the GitHub UI with one click and reads the PASS/FAIL table in the Actions log. Without this path, onboarding verification is blocked for operators without local CLI access. ⚠️ Inferred from onboarding lens: a new project added today requires significant human intervention; the verify-onboarding path requires local credentials at exactly the moment they may not be available; a GitHub-UI-triggerable verification removes this friction.

### Lens 5 — Visibility: human cannot quickly answer 3 key questions

- 🔲 46.12 — `docs/aide/` README or index file must exist and be kept current — the first file a new observer reads after README.md should be a clear directory map of what otherness writes and why: a new team member opening the repo sees `README.md` (describes what otherness is) and then `docs/aide/` (where otherness writes its outputs). But `docs/aide/` has no index file — no `README.md` or `INDEX.md` explaining what each file is, who writes it, and what a human should read to answer each question. The observer must open each file to understand its purpose. SM §4g must generate and maintain `docs/aide/README.md` (a 20-line file auto-generated on first run, then updated when new files are added): one row per file with columns: `file`, `written by`, `updated`, `answers`. Example: `| metrics.md | SM §4b | every batch | How many PRs did we ship? Is the rate trending up? |`. When a new file is added to `docs/aide/` (by any agent): SM §4g must add a row for it in the next batch. When a file is not updated for >20 batches: mark its row "⚠️ stale". Without this index, `docs/aide/` is an undocumented accumulation of files — the observer must read each one to understand the system, and the system provides no guidance. A 20-line README in `docs/aide/` is the single highest-leverage visibility improvement that requires no new infrastructure. ⚠️ Inferred from visibility lens: a human looking at GitHub right now cannot quickly orient in the otherness output structure; there is no guide to what docs/aide/ contains; the absence of an index file is the first friction point for every new observer.

- 🔲 46.13 — Session branch naming must encode enough context for the operator to understand what ran without clicking into the branch — the current `opencode/schedule-<date>-<hash>` format is opaque: `git branch -r` on the repo shows branches like `opencode/schedule-2026-04-22-a3b1c2`. A human looking at the branch list cannot tell: (a) whether the run was Step A (vision scan) or Step B (run), (b) whether the run shipped anything, or (c) what the batch number was. When multiple branches are open (a failed cleanup from a prior session), the operator cannot triage without opening each branch's last commit. SM §4g must rename the session branch before pushing the final `_state` commit to the format: `opencode/batch-<N>-<GREEN|AMBER|RED>-<meaningful_prs>pr`. Example: `opencode/batch-42-GREEN-2pr` or `opencode/batch-43-AMBER-0pr`. SM §4g must use `git branch -m <old> <new>` before the final push. The branch name is a zero-click health signal: a human doing `git branch -r | grep opencode` sees the last 5 branches and reads "batch-42-GREEN-2pr, batch-43-AMBER-0pr, batch-44-GREEN-1pr" — instantly knows the trend without opening anything. ⚠️ Inferred from visibility lens: a human looking at GitHub right now cannot quickly tell if the system is healthy; branch names are an underused zero-click visibility surface; the current naming convention is timestamp-based and conveys no health information.

- 🔲 46.14 — Vision scan Step A run must be distinguished from batch Step B run in the GitHub Actions history — operators cannot currently tell which workflow run did what: the `otherness-scheduled.yml` dual-step workflow runs Step A (vibe-vision-auto) and Step B (otherness.run) in the same workflow execution — they appear as a single green ✓ in the Actions tab. When a run produces a vision scan commit but no PR (Step A ran, Step B found nothing to claim), the operator sees a green run and cannot tell from the Actions history whether Step B actually ran or was skipped. The workflow must add a job-level name annotation: the Step A job should be named "Vision Scan (Step A)" and the Step B job "Run (Step B)" in the workflow YAML. Additionally, the Step A job must output its scan summary to `$GITHUB_STEP_SUMMARY`: "Vision scan complete: [N] items promoted, [M] stale flagged, [K] inferred added." The Step B job output is specified in doc 28 (28.2). With both outputs, a human clicking on any workflow run in the Actions tab sees two distinct job summaries — one for the vision scan and one for the session run — without needing to read log lines. ⚠️ Inferred from visibility lens: the dual-step scheduled workflow is a key system component but produces a single undifferentiated entry in the Actions history; operators cannot distinguish "Step A ran, Step B skipped" from "both steps ran and shipped"; distinguishing the two requires reading raw logs.

### Newly surfaced gaps (2026-04-22 third vision scan — SCAN 5 scored 0/5 pressure bullets addressed)

- 🔲 46.18 — COORD must post a structured session-outcome summary to the report issue when SM §4f fails to run — the health signal must not depend on a single agent completing: SM §4f is responsible for posting the per-batch health comment. But if SM §4f fails to run (LLM timeout, phase exit before SM, session budget exhausted in ENG/QA), the batch completes with no health signal at all. A human looking at the report issue sees the last successful batch's comment — with no indication that the current batch ran or failed. COORD §1d-exit must add a minimal session-outcome post as its final step before the session ends: `gh issue comment $REPORT_ISSUE --body "[SESSION OUTCOME | COORD] Session exiting. Items claimed: N.
