## Future (🔲)

### Lens 1 — Reliability: meaningful PR every run, silent failures

- 🔲 48.1 — The "at least one meaningful PR per run" SLA has no enforcement at the COORD entry point — it must be a hard pre-claim requirement, not a post-hoc detection: items 46.20 (SM §4b detects zero-output at session END) and 46.28 (COORD starvation emergency protocol) address detection after the fact or when the queue is empty. But the most reliable reliability improvement is a COORD §1b pre-claim gate: before claiming ANY item, COORD must evaluate whether the item is achievable in the current session's remaining budget. If the item's estimated size exceeds the estimated remaining tokens (from OpenCode's context window), COORD must split the item or select a smaller substitute. Currently COORD claims whatever is highest priority, regardless of session budget remaining. A session that claims a `size/xl` item in the last 20% of its context window will produce a partial implementation, open a half-finished PR, and fail QA — wasting both the claim and the budget. COORD §1b must add a `size_budget_check`: read `remaining_context_pct` from OpenCode's current context estimate; if `remaining_context_pct < 30%` AND the top queue item is `size/l` or `size/xl`: skip it and claim the next `size/xs` or `size/s` item instead. Cap at one `size/xs` claim per session when context is low. Log: "COORD §1b: low context — claiming size/xs item instead of size/xl to guarantee session output." Without this gate, late-session claims produce the worst outcomes: items claimed but not completed, QA failures on partial implementations, and silent zero-output exits that look like normal session ends. ⚠️ Inferred from reliability lens: sessions still fail silently; one specific and preventable cause is late-session claims of large items that cannot complete before context runs out; no current gate checks session budget before claiming.

- 🔲 48.2 — The stale watchdog must verify that reclaimed items have a root cause comment before re-releasing to the queue — not just a label change: SM §4a stale watchdog detects items stuck in `in_progress` for >60 minutes and returns them to `todo`. This prevents items from disappearing forever. But the stale watchdog does not ask WHY the item went stale — it just releases it. The next session claims the same item, encounters the same blocker, and the stale watchdog fires again. After 3 stale-watch cycles, the item effectively cycles indefinitely. The stale watchdog must: (1) when reclaiming a stale item, check the last GitHub issue comment for the item — was there a `[ENG BLOCKER]` comment or a `[QA REJECT]` comment in the last session? (2) If yes: add label `blocked` and post a diagnostic comment: "⚠️ Stale watchdog: this item has gone stale 3x. Last session blocker: [extracted text]. Changing priority from high→medium and adding blocked label until blocker is resolved." (3) If the item has gone stale 5x with the same root cause pattern: change status to `needs-human` and open a `[NEEDS HUMAN: persistent-stale-item]` issue. Without root-cause analysis in the stale watchdog, the system can cycle on the same blocked item indefinitely while reporting GREEN health (the item never disappears — it just keeps going stale). ⚠️ Inferred from reliability lens: sessions still fail silently; the stale watchdog is a recovery mechanism but not a learning mechanism; it returns items to the queue without any diagnosis of why they went stale; persistent stale items are a reliability anti-pattern the system perpetuates.

- 🔲 48.3 — ENG must write a structured `[ENG OUTCOME]` comment to the GitHub issue before closing the PR — not just open the PR and exit: currently ENG opens a PR and moves on. If QA rejects the PR, the issue stays open with only the PR rejection comment visible. A new session that re-claims the same issue must read the PR rejection comment, understand the QA rejection reason, and plan a different approach — without any structured summary of what ENG attempted and why it failed. ENG §2f must write a structured `[ENG OUTCOME]` comment to the issue at PR-open time: "PR opened: #N. Approach: [1-sentence description of implementation strategy]. Files changed: [list]. Design doc obligations addressed: [list]. Known limitations: [any spec obligations skipped or partially implemented, with reason]." QA §3a must read this comment before reviewing. When QA rejects: QA must respond to this comment with a structured `[QA REJECTION]` comment: "Rejected: [specific obligation failed] — [what ENG did vs. what spec requires]." The next ENG session reading the issue thread sees: what was tried, why it was rejected, and what specific change is needed. Without this structured comment chain, re-implementation attempts start from scratch every session — the system has no issue-level memory of what failed. ⚠️ Inferred from reliability lens and self-improvement lens: sessions fail silently because there is no issue-level memory of previous attempts; ENG and QA communicate via PR diff and review comments but the issue itself has no implementation history; the [ENG OUTCOME] comment is the minimum artifact that gives the next session context for re-implementation.

### Lens 2 — Honesty: SM says GREEN but products not advancing

- 🔲 48.4 — The honesty score (doc 45, item 45.1) has no adversarial review of its own components — it can be self-confirming: item 45.1 defines `loop_honesty_score` with four components (delivery_honesty, sim_honesty, skills_honesty, doc_honesty). Each component is computed by the same SM §4f phase that reports the score. A component like `doc_honesty` measures "ratio of ✅ Present items verifiable against agent files" — but SM §4f is also the phase that marks items ✅ Present. A phase that marks items ✅ Present and then computes its own doc_honesty score has a structural incentive to be lenient with ✅ Present markings (lenient marking = higher honesty score). No external agent or mechanism provides a second opinion on whether the honesty score components are computed correctly. PM §5 must add a `honesty_score_adversarial_check` every 20 batches: (1) re-compute `doc_honesty` independently by sampling 10 random ✅ Present items and checking agent files for the described behavior — using the SAME heuristic as SM §4f but executed by PM §5 code (different phase, same data); (2) compare PM's `doc_honesty_independent` to SM's `doc_honesty_reported`; (3) if they differ by >15 points: post to report issue: "⚠️ Honesty score divergence: SM reports doc_honesty={N} but PM independent check yields {M}. Possible over-reporting. Investigate SM §4f doc_honesty component." Without this check, the honesty score can be consistently over-reported by the very phase that benefits from a higher score — a self-confirming metric that defeats the purpose of measuring honesty. ⚠️ Inferred from honesty lens: the loop is not honest enough; the honesty score (45.1) is computed by SM §4f which is the same phase that makes decisions honesty measures; a self-administered honesty test is not independent; adversarial cross-checking by PM is the minimum independence gate.

- 🔲 48.5 — Managed project advancement must be measured by user-visible outcomes, not PR count — PRs on a docs-only project can look productive while the product stalls: the `managed_project_honesty_check` (45.4) counts `feat/` prefix PRs merged in the last 7 days. But a managed project that ships 5 `feat/docs` PRs (documentation improvements) passes the check while shipping 0 user-facing features. The check conflates "project is active" with "project is advancing." PM §5 must distinguish three categories for each managed project: (1) `user_visible_change`: PR changes code that runs in production (`src/`, `lib/`, `app/`, language-specific source directories — not `docs/`, not config files); (2) `infrastructure_change`: PR changes CI, tooling, or dev environment; (3) `docs_only`: PR changes only documentation. The managed project advancement check must require ≥1 `user_visible_change` PR per 7 days to avoid fleet-stall detection. A project that ships only infrastructure and docs PRs for 14 days is strategically stalled — the user's product is not advancing. PM §5 must report: "Fleet: [project] — 7d activity: 2 user-visible, 3 infra, 5 docs-only. User-visible: ⚠️ low (< 2/week threshold)." Without this classification, the fleet monitor rewards documentation activity at the expense of product delivery — the most visible honesty failure in multi-project management. ⚠️ Inferred from honesty lens: the loop is not honest enough; the SM health signal says GREEN but the products it manages may not be advancing from the user's perspective; PR count includes documentation and infrastructure work that does not change user outcomes.

- 🔲 48.6 — The simulation's `recovery_action` field must be verified as human-readable before it is acted upon — unclear actions are silently ignored: COORD §1b-preflight reads `recovery_action` from `_state:sim-prediction.json`. The field values are strings like `trigger_learn`, `reduce_batch_size`, `focus_on_honesty_items`. But the field is written by `scripts/calibrate.py` which is a Python script — if the script produces an unexpected output (empty string, Python traceback fragment, `None` literal), COORD silently falls through the recovery action check with no error. A `recovery_action` of "reduce_batch" (missing the `_size` suffix) is not recognized and is silently ignored — COORD continues with normal behavior while the simulation intended a specific intervention. SM §4e must validate `recovery_action` before writing it to `sim-prediction.json`: (1) define an allowlist of valid values: `["none", "trigger_learn", "reduce_batch_size", "focus_on_honesty_items", "increase_queue_depth", "pause_feature_work"]`; (2) if `calibrate.py` produces a value outside the allowlist: write `recovery_action: "none"` with a `recovery_action_invalid: true` flag and a `recovery_action_raw` field containing the original value; (3) SM §4e must post to the report issue when `recovery_action_invalid: true`: "⚠️ Simulation produced unrecognized recovery_action: '[raw value]' — treated as none." Without this validation, recovery actions can silently fail to trigger because of minor format differences between what calibrate.py produces and what COORD expects — a classic integration gap between two components with no shared schema. ⚠️ Inferred from honesty lens: the simulation exists but its predictions are not visibly changing agent behavior; one reason is that the recovery_action field has no validation gate — invalid values are silently treated as none.

### Lens 3 — Self-improvement: monoculture, skill growth, agents not smarter

- 🔲 48.7 — Skill loading must be tracked per ENG session and linked to session outcomes — "which skills made a measurable difference?" must be answerable: `agents/skills/` has 14 files. ENG loads skills based on relevance heuristics. But no mechanism tracks: (1) which skills were loaded in each session, (2) whether the session's outcome differed when specific skills were loaded vs. not, and (3) whether a skill's load frequency is correlated with better or worse QA outcomes. This data is available: the ENG PR description should contain "Loaded skill: [file]" (per the skill-loading instruction), and QA outcome (approved/rejected) is observable. SM §4b must add a `skill_impact_tracker`: every 20 batches, parse "Loaded skill:" lines from the last 20 ENG PR descriptions, build a table of `skill → sessions_loaded → qa_approved → qa_rejected`, and post to the report issue: "📚 Skill impact (last 20 sessions): [table]." A skill with 0% QA approval after 5 loads may be providing wrong advice. A skill that is never loaded despite relevant sessions may be indexed incorrectly. Without this tracking, the skills library grows without any feedback on whether individual skills are helping. ⚠️ Inferred from self-improvement lens: the agents are not meaningfully smarter because the skill library grows without evidence that individual skills improve outcomes; there is no feedback loop from skill loading to session quality; skill impact tracking converts the library from a static archive into a living, evidence-based knowledge base.

- 🔲 48.8 — The `agents/skills/` directory has no quality decay mechanism — skills written for an older architecture remain loaded even after the architecture changes: `agents/skills/` currently has 14 files. Skills added in batch 5 described patterns for a standalone.md that has since been refactored. A skill that says "always write state to `.otherness/state.json`" might be accurate for batch 5 but incorrect after state management was moved in batch 50. ENG loads this skill and follows outdated advice — which may pass QA (because QA doesn't check against the skill) but produces wrong behavior. SM §4b must, every 30 batches, run a `skill_decay_check`: for each skill file in `agents/skills/`, extract the top 3 file references (e.g., "`standalone.md`", "`agents/phases/sm.md`") and verify each referenced file still exists and still contains the referenced section or behavior. If a skill references "`standalone.md §2f`" but that section was renamed to "`§3a`" in a recent refactor: flag the skill: add a `⚠️ Stale — §2f not found in standalone.md` comment to the top of the skill file and post an issue: "Skills decay detected: `[skill-file]` references sections/files that no longer exist — review and update." Without this check, the skills library accumulates dead or misleading guidance that ENG silently follows — a self-improvement mechanism that degrades quality over time instead of improving it. ⚠️ Inferred from self-improvement lens: the agents are not meaningfully smarter because the skills library has no freshness check; skills written for an older architecture degrade in quality as the system evolves; a decay check is the mechanism that keeps the library honest as the architecture changes.

- 🔲 48.9 — The learn sessions have no outcome quality gate — a learn session that produces a skill the system already knows is counted as a successful session: PROVENANCE.md tracks learn sessions with `paradigm_category`, `source_repo`, and `skills_extracted`. But no mechanism checks whether the extracted skills are genuinely novel relative to the existing library. A learn session on a React codebase can extract "break complex components into smaller, focused components" — a principle already implicit in `declaring-designs.md`. The skill is logged, PROVENANCE.md gets an entry, SM §4c counts it as a successful learn session, but the library contains duplicate guidance in different words. This is the "slow skill growth" problem from the pressure context: the learn sessions run but the agents aren't meaningfully smarter because the new skills restate what is already known. Before a learn session is closed: `agents/otherness.learn.md` must add a DUPLICATE FILTER step: (1) for each candidate skill extracted, embed the skill text as a 20-word summary; (2) run a pairwise similarity check against all existing `agents/skills/*.md` files (Python difflib or keyword overlap); (3) if similarity score > 70% for any existing skill: mark the candidate as DUPLICATE and do not write it; (4) if ≥50% of candidates are duplicates: write a PROVENANCE.md entry noting "low novelty session — [N/M] skills rejected as duplicates" and consider this a low-quality learn outcome. Without this filter, the learn sessions optimize for volume (new file written = success) rather than novelty (genuinely new knowledge added). ⚠️ Inferred from self-improvement lens: the skills library grows slowly because there is no filter that distinguishes "new file written" from "genuinely new knowledge added"; duplicate skills create noise in the library and over-count successful learn sessions.

### Lens 4 — Onboarding: new projects require human intervention

- 🔲 48.10 — `/otherness.onboard` has no regression test — a change to `onboard.md` can break the generated `docs/aide/` files without detection: `onboard.md` was audited and fixed in Stage 3. But since Stage 3 completed, ENG has made ~100 PRs that may have touched `agents/onboard.md` indirectly or modified the expected output format. There is no automated test that runs `/otherness.onboard` against a test fixture and verifies the generated `docs/aide/` output meets the Stage 3 acceptance criteria. `scripts/test.sh` integration test checks `_state` branch activity on the reference project — it does not test the onboarding output. A regression test for onboarding is: (1) run `/otherness.onboard` against a minimal test fixture repo (or a known-good snapshot of an existing project's codebase); (2) verify the generated `docs/aide/vision.md`, `docs/aide/roadmap.md`, `docs/aide/definition-of-done.md` all contain non-empty, non-placeholder content; (3) verify `docs/design/` directory contains at least 1 stub; (4) verify `otherness-config.yaml` has non-empty `schedule.cron` and `pr_label` fields. This test must be added to `scripts/test.sh` as a new check (check 6). Without this regression test, any change to `onboard.md` — or to the config template it uses — can silently break the onboarding flow, requiring humans to diagnose the failure when the next real project is onboarded. ⚠️ Inferred from onboarding lens: a new project added today would still require significant human intervention; the Stage 3 improvement is not protected by a regression test; the onboarding quality can degrade with any PR that touches onboard.md or its dependencies without detection.

- 🔲 48.11 — The onboarding guide (`onboarding-new-project.md`) has no "expected time" or "what you will see" milestones — a new operator cannot tell if onboarding is progressing normally or stuck: a new operator following `onboarding-new-project.md` runs a sequence of `gh` commands. After step 7, they wait for the first scheduled run. They have no guidance on: how long the first run takes, what they should see in the Actions log if it's working, what failure modes look like, and when to assume something went wrong vs. still in progress. The guide is a sequence of commands with no progress indicators. `onboarding-new-project.md` must add a "What to expect" section after each major step group: Step 3 (secrets): "After this step: run `gh secret list --repo <REPO>` — you should see OPENCODE_API_KEY listed." Step 6 (workflow enable): "After this step: in the GitHub Actions tab, you should see `otherness-scheduled` listed as Enabled." Step 7 (first run): "The first run will take 15–30 minutes. The Actions tab should show a running workflow within 1 hour of the cron time. If no run appears after 2 hours: check that the workflow is enabled and that the OPENCODE_API_KEY secret is valid." Concrete checkpoints convert an ambiguous wait into a structured verification process. A new operator who waits 6 hours with no run and no guidance will assume failure and ask for help — but 90% of "no runs" are caused by a disabled workflow (checkable in 30 seconds). The guidance should prevent this from ever requiring human escalation. ⚠️ Inferred from onboarding lens: a new project added today would still require significant human intervention; the setup guide is incomplete in the sense that it does not prepare the operator for the waiting periods and verification steps between major actions; operators fail during the gaps between commands, not during the commands themselves.

- 🔲 48.12 — `otherness-config.yaml` new project template has no minimum validation — a project onboarded with missing required fields silently runs in a broken state: `otherness-config-template.yaml` has all the fields. But if an operator copies it, renames the repo, and forgets to fill in `report_issue`, the first session computes `$REPORT_ISSUE=""` and all `gh issue comment "" ...` calls fail silently (gh returns error but the loop continues). The session "succeeds" from a CI perspective but writes no health comments and creates no audit trail. `/otherness.setup` and `/otherness.onboard` must add a config validation step at the end: parse `otherness-config.yaml` and verify each required field is non-empty: `project.name`, `project.report_issue`, `project.pr_label`, `schedule.cron`. For each empty field: print "⚠️ Missing required config field: [field]. Run will proceed but [consequence] will be missing." Block the onboarding completion message until all required fields are filled. Currently the validation only checks file existence (`scripts/validate.sh`), not field completeness. A partially-filled config is worse than no config: the system runs, claims it succeeded, and leaves no trace of the health signals the operator depends on. ⚠️ Inferred from onboarding lens: a new project added today would still require significant human intervention; the most common setup error (missing report_issue) causes silent failures that are invisible until the operator checks the report issue and finds nothing there; field validation at onboarding time prevents this class of failure entirely.

### Lens 5 — Visibility: human cannot answer 3 key questions in 30 seconds

- 🔲 48.13 — The report issue comment model has no "pinned latest" mechanism — a human arriving at the issue after a long absence must scroll past 30+ old comments to find the current state: item 39.2 adds a health table to the report issue BODY (not a comment), which pins the current state to the top. But 39.2 is not yet shipped. Until it ships, a human who opens the report issue after 30 batches sees the oldest comment at the top (GitHub default sort order) and must scroll to the bottom to find the latest health signal. The immediate fix (before 39.2 ships) is: SM §4f must add a persistent "current status" comment by EDITING the same comment each time (using `gh api --method PATCH repos/$REPO/issues/comments/<static-comment-id>`) rather than posting a new comment. SM §4g must store the `health_comment_id` in `state.json` from the first batch it posts one. All subsequent batches must EDIT that comment, not post a new one. A human arriving at the report issue sees one comment at the top from "otherness[bot]" that contains the current health table — always the same comment, always up to date. This avoids the 30-entry scroll and does not depend on 39.2 shipping first. The approach: first batch creates comment, stores comment ID; all subsequent batches edit it. ⚠️ Inferred from visibility lens: a human looking at GitHub right now cannot quickly tell if the system is healthy; the "30+ comment scroll" problem is live and worsening every batch; the pinned-edit approach is a zero-dependency fix that can ship before 39.2 and provides immediate visibility improvement.

- 🔲 48.14 — `docs/aide/` staleness is undetectable from a GitHub mobile view — the "Updated: [date]" line in each file is the only timestamp and it is buried in the file body: a human checking system health on a mobile device opens `docs/aide/progress.md` and sees the header "otherness: Current Progress" followed by prose. The "Last update" date is on line 3 — visible only after scrolling past the H1. If the file is >2 screens on mobile, the human may not see the date at all. The date is the most critical field: it tells the reader whether the data is current or stale. Each `docs/aide/*.md` file must begin with a YAML frontmatter block (lines 1–3): `---\nlast_updated: YYYY-MM-DD\nbatch: N\n---`. SM §4f must write this frontmatter to each `docs/aide/*.md` file it updates. GitHub renders frontmatter as metadata, not as body text — it appears as a small grey box at the top of the file on both desktop and mobile, immediately visible without scrolling. The `batch: N` field is the human-readable equivalent of "this data is from 3 hours ago" — it tells the reader how fresh the information is relative to the current batch count in the health comment. Without frontmatter, the staleness of docs/aide/ files is undetectable on first view — a human on mobile cannot tell in 30 seconds whether they are reading today's data or last week's. ⚠️ Inferred from visibility lens: a human looking at GitHub right now cannot quickly tell if the system is healthy; specifically, they cannot tell if the `docs/aide/` files they are reading are current without scrolling to find the update date; YAML frontmatter is the zero-change-required fix that makes freshness immediately visible on any device.

- 🔲 48.15 — The three key questions ("is it healthy?", "what did it ship today?", "is it moving toward the vision?") have no single combined answer — a human must open 3 separate places to answer all three: item 39.2 puts the health table in the report issue body. Item 39.3 syncs it to `docs/aide/progress.md`. Item 39.24 adds a Roadmap row to the health table. But even when all three items ship, a human still needs to: (1) open the report issue for the health table, (2) open the latest merged PR for "what did it ship today?", (3) open `docs/aide/roadmap.md` for "is it moving toward the vision?". The three-question answer is spread across three separate URLs. SM §4f must create a single `docs/aide/HEALTH.md` file that contains all three answers in ≤20 lines: (1) Health section: 3-row table (health signal, last batch, key metric); (2) Latest delivery section: one-sentence description of the top PR from the last session; (3) Direction section: one-sentence roadmap progress ("Stage 11: 4/6 deliverables — +1 this week"). SM §4g must commit this file every batch. A human bookmarking one URL (`docs/aide/HEALTH.md`) gets all three answers from one page. This is the minimal single-page health dashboard the pressure context asks for — not a web dashboard, not an API endpoint, but a committed markdown file updated every batch that answers all three questions on one screen. ⚠️ Inferred from visibility lens: the pressure context explicitly says "there is no clean single-page health dashboard"; the answer is not an external tool — it is a committed markdown file that aggregates the three key questions into one URL; docs 39 items solve the component pieces but no item specifies the aggregate single-file view.

## Zone 2 — Implementer's judgment

- 48.1 (size budget check): the `remaining_context_pct` estimate does not need to be
  precise — a rough heuristic (e.g., session is in its 3rd item claim) is sufficient
  to trigger the size downgrade. Exact context window measurement is unnecessary.
- 48.3 (ENG OUTCOME comment): the comment should be ≤200 words. The goal is structured
  recall for the next session, not a detailed post-mortem.
- 48.13 (pinned-edit comment): the `health_comment_id` stored in state.json must survive
  state branch pruning. SM §4g must ensure this key is not dropped during state compaction.
- 48.14 (YAML frontmatter): some GitHub renderers display frontmatter as a table at the
  top of the file; others hide it. Test the rendering in the GitHub web UI before shipping.
  If rendering is unexpected, use an H6 first-line header `###### Updated: YYYY-MM-DD | Batch: N`
  as an alternative that is always visible at the top.
- 48.15 (HEALTH.md): this file must not duplicate the detail of `progress.md` or
  `metrics.md`. It is a summary, not a source of truth. ≤20 lines. No tables with more
  than 3 rows. The goal is 30-second readability, not completeness.
