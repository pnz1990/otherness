## The problem

The tenth scan reveals that recent work has addressed symptoms while leaving root causes intact.
SCAN 5 now scores 5/5 "addressed" due to over-broad domain noun matching (PR #932 expanded nouns
so broadly that 'health', 'metrics', 'session' match hundreds of unrelated Present items). This
produces a false signal: the pressure rewrite fires every scan even though nothing in the pressure
lens has actually been resolved. Meanwhile, all five lens areas remain genuinely open.

This doc captures five new gaps — specific to the failure modes still live as of batch 14 / 2026-04-23 —
that are NOT covered by any existing design doc item.

## Future (🔲)

### Lens 1 — Reliability

- 🔲 50.1 — The "silent session failure" mode has two subtypes that require different fixes, but the current detection mechanism treats them identically: PR #878 added a workflow heartbeat step, and PR #904 added a post-run assertion step for the job summary. Both detect that a session ended with 0 meaningful PRs. But they do not distinguish: (A) session completed its loop and genuinely found no shippable work, vs (B) session terminated abnormally (crash, timeout, API error mid-phase) before the loop completed. Subtype A requires a vibe-vision scan or queue enrichment. Subtype B requires a restart with root-cause diagnostics. Today, both subtypes produce the same output: a job summary noting 0 PRs and a COORD chore fallback on the next run. The SM §4f health comment does not distinguish these subtypes, so the operator cannot tell which recovery action is needed. SM §4f must classify session outcomes into: `completed_zero_prs` (loop ran fully, no work found) vs `terminated_early` (loop exited before SM §4f ran, evidenced by missing SM comment or missing `_state` update). The health comment must surface this classification: "⚠️ Last session: TERMINATED EARLY — recovery: restart with diagnostics" vs "⚠️ Last session: COMPLETED, 0 PRs — recovery: run vibe-vision or enrich queue." Without this classification, the operator applies the wrong recovery action — queue enrichment when the loop crashed, restart when the queue was empty. ⚠️ Inferred from reliability lens: sessions still fail silently; the heartbeat+post-run assertion detect the symptom; this item adds the cause classification that drives the correct recovery action.

- 🔲 50.2 — The `chore-only guard` (COORD §1d, PR #902) uses a static `kind/chore` label check but does not distinguish between chore items that unblock feature work (high-ROI chore) and chore items that produce cosmetic changes (zero-ROI chore): the guard fires when all claimable items are `kind/chore`. It then triggers queue enrichment. But queue enrichment is a 3-step process (COORD §1b-session-type) that takes most of the session budget. If the single available chore item would unblock 5 feature items (e.g., "fix broken test harness"), the guard wrongly defers it to run enrichment instead. COORD §1d must classify chore items as `blocking` (has label `chore/unblocks-feature` or the body contains "unblocks: #N") vs `cosmetic` (all other chores). The chore guard must: claim `blocking` chores immediately (they are feature-enabling, not pure chores); only trigger enrichment for `cosmetic`-only chore queues. This requires ENG/QA to apply `chore/unblocks-feature` when opening a chore PR that explicitly unblocks an issue. Without this distinction, the guard defers blocking chores and wastes a session on enrichment when the highest-ROI action was a 2-line fix. ⚠️ Inferred from reliability lens: the chore gate improved but blocking chores and cosmetic chores are treated identically; the zero-ROI failure mode (deferring a blocking chore for enrichment) is new and not covered by any prior design doc.

### Lens 2 — Honesty

- 🔲 50.3 — SCAN 5 domain noun expansion (PR #932) created an over-broad matching problem: domain nouns like 'health', 'metrics', 'session', 'learn', 'skill', 'agent', 'report' appear in 100+ Present items unrelated to the pressure bullet's intent — causing all 5 bullets to score "addressed" every scan, making the rewrite item permanent noise: the intent of domain noun expansion was to resolve abstract bullets (e.g. "Is the onboarding good enough?") that never matched PR titles literally. The implementation extracted too many generic terms. 'health' matches `feat(sm): §4f health comment`, `feat(sm): degrade health to AMBER`, etc. — these are health-signal improvements, not the "single-page health dashboard" the pressure bullet asks about. The over-matching means: (1) SCAN 5 fires the rewrite item every single run (5/5 = 100% > 60% threshold), (2) rewrite items accumulate in design docs as noise, (3) SCAN 5 is now less honest than the broken first-30-char version it replaced. The fix requires PRECISION BOUNDS on domain noun scoring: each domain noun must be categorized as `primary` (specific to this lens, high confidence) or `secondary` (shared across lenses, low confidence). A bullet is "addressed" when ≥3 primary-noun matches OR ≥5 total matches — not ≥2 total. 'dashboard', 'single-page', '30-second' are primary nouns for the visibility bullet. 'health' is a secondary noun. The rewrite threshold must also increase from 60% to 75% to avoid triggering on normal delivery. Without precision bounds, SCAN 5 produces a permanent false-positive and the pressure rewrite mechanism — designed to evolve the vision — becomes automated noise. ⚠️ Inferred from honesty lens: the loop's own self-assessment tool (SCAN 5) is now self-confirming; metrics are being collected (SCAN 5 runs) but the metric is wrong; this item corrects the measurement instrument.

### Lens 3 — Self-improvement

- 🔲 50.4 — Skill extraction was added to `/otherness.learn` (PR #919) but there is no routing from "skill extracted" to "ENG uses that skill on the next applicable claim" — skills are written to files but not read at claim time: PR #919 added a skill-extraction contract: learn sessions must write skills to `agents/skills/`. PR #936 added skill-load verification: ENG §2c must load a skill and cite it in the PR. But neither item connects extraction to routing: COORD §1b does not read `agents/skills/` when selecting a claim and does not annotate the issue with "suggested skill: agents/skills/foo.md". ENG §2c loads A skill but not necessarily the MOST RELEVANT one — selection is based on ENG's own judgment from README.md. The routing gap means: a skill extracted from a learn session on "database migration patterns" will never be loaded by an ENG session working on a database migration issue unless ENG happens to read README.md, recognizes the match, and loads it. This is exactly the "agents are not meaningfully smarter" failure mode. COORD §1b-claim must, after selecting an issue to claim, scan `agents/skills/README.md` for skill entries whose `applies-to` tag matches the issue's area labels (e.g., `area/agent-loop`, `area/onboarding`). Write to the claimed issue: "🎯 Suggested skill: `agents/skills/foo.md` — load at ENG §2b." ENG §2b must prefer COORD-suggested skills over self-selected ones. Without routing, skill extraction and skill loading are two disconnected loops that never close. ⚠️ Inferred from self-improvement lens: skills are extracted (PR #919) and loading is verified (PR #936) but the connection — COORD routing specific skills to specific claims — is missing; this is the gap that keeps agents from being meaningfully smarter.

### Lens 4 — Onboarding

- 🔲 50.5 — `/otherness.onboard` has no idempotency or resume support — when it fails midway (GitHub API error, rate limit, missing secret), the operator must start over from scratch, re-running steps that already succeeded and risking duplicate issues or overwritten docs: `agents/onboard.md` STEP 1–8 write files, create issues, open PRs, and push to the repo. If the agent crashes at STEP 5, STEPs 1–4 have already modified the repo. The next run re-executes all steps: it re-creates issues (creating duplicates), re-writes files (clobbering any manual fixes), and re-pushes (potentially force-pushing). No `state.json` field records onboarding progress. The fix: `onboard.md` must write an `otherness-onboarding-state.json` file to the target repo after each major STEP group completes, containing: `{"completed_steps": [1, 2, 3], "last_error": null, "started_at": "..."}`. At startup, read this file: if it exists, skip completed steps. This makes each step group idempotent: re-running a completed step is a no-op. The file must be removed from the repo (or moved to `.otherness/`) when onboarding completes. QA §3a must check that no duplicate issues were opened during the session. Without idempotency, every partial failure during onboarding requires full manual cleanup — exactly the "significant human intervention" the pressure lens identifies. ⚠️ Inferred from onboarding lens: a new project added today would still require significant human intervention; one underdiagnosed source of that intervention is failed-midway onboarding requiring manual cleanup; this item eliminates that class of failure.

### Lens 5 — Visibility

- 🔲 50.6 — The "3 questions in 30 seconds" user journey test (doc 49.11) has been specified but has never been run — not in any batch, not as part of any QA check — meaning the entire visibility work stream can ship without ever testing the actual user goal: doc 49.11 specifies a PM §5 periodic test. But PM §5 has not been updated to include it, and no batch has run it. This is not a "spec not shipped" problem — it is a "test that was never scheduled" problem. The test must be scheduled explicitly. PM §5 must include step §5q: "30-second visibility test" — runs every 10 batches (not 20, given the urgency of the visibility gap). The test procedure is exactly as specified in 49.11. PM §5q must be added to `agents/phases/pm.md` as a non-optional step, not deferred until a design doc is marked ✅. The rationale for mandatory inclusion before the design doc ships: the visibility gap is the MOST HUMAN-OBSERVABLE failure mode in the system. Every other lens failure (reliability, honesty, self-improvement, onboarding) can be masked. The visibility failure cannot — a human looking at GitHub RIGHT NOW can confirm or deny it in 30 seconds. Running the test at PM §5q makes visibility failure immediately surfaceable rather than pending a design doc PR. Without mandatory scheduling in pm.md, 49.11 remains a design doc item with no execution path — it will be implemented "eventually" while the visibility gap persists indefinitely. ⚠️ Inferred from visibility lens: there is no clean single-page health dashboard; the test that would confirm this is unambiguously missing; it must be mandatory and immediate, not deferred.
