# 33: Stage 4 — Self-Improvement Metrics

> Status: Complete | Created: 2026-04-20

---

## What this does

Generates quantitative evidence of the system's own improvement over time. The SM
phase updates metrics after every batch. PM validates metrics for stagnation and
opens proactive improvement issues.

## Future (🔲)
- 🔲 Metrics schema must include `meaningful_prs` and `session_items_completed` columns: the existing schema tracks `prs_merged` (total) but cannot distinguish a session that shipped 5 feature PRs from one that shipped 5 chore PRs. `meaningful_prs` (count of PRs advancing a 🔲→✅ transition) and `session_items_completed` (items attempted in the multi-item loop) are the two columns needed to detect the "housekeeping-only" failure mode described in doc 21. SM §4b must write both. PM §5 stagnation check uses `meaningful_prs` as its primary velocity signal. Without these columns, the stagnation check is a proxy (todo_shipped) that cannot distinguish real forward progress from chore accumulation. ⚠️ Inferred from honesty lens: current metrics schema cannot prove the system is shipping meaningful work.
- 🔲 Metrics data must drive agent behavior changes, not just observations: today, when SM detects a regression (needs_human up 2 consecutive batches), it opens an issue. But it does not adjust agent behavior in the current session or the next. The loop between "metrics indicate a problem" and "agent changes behavior to fix it" requires a human to read the issue and act. This loop must be closed. SM §4b must write a `next_session_directive` field to `state.json` when it detects a regression — e.g. `{"directive": "prioritize_ci_fix", "reason": "ci_red_hours > 2 for 3 batches"}`. COORD §1b must read this field at session start and reorder claims accordingly. Metrics that do not change behavior are dashboards, not instruments. ⚠️ Inferred from honesty lens: simulation exists and metrics are collected but predictions are not visibly changing agent behavior.
- 🔲 `skills_count` trajectory tracked in metrics.md: the schema tracks `prs_merged`, `needs_human`, `ci_red_hours` and others, but `skills_count` (total skills in `agents/skills/`) is not recorded per batch. A system that claims self-improvement should show skills growing over time — but this trajectory is invisible in the current schema. SM §4b must add a `skills_count` column (count of `*.md` files in `agents/skills/` minus `README.md` and `PROVENANCE.md`) written every batch. PM §5 stagnation check must flag when `skills_count` has not changed in 30 batches — this is strong evidence that `/otherness.learn` has stopped running. A flat `skills_count` for 30 batches + no PROVENANCE.md update = the self-improvement loop has silently stopped. ⚠️ Inferred from self-improvement lens: skills library grows slowly; no metric currently captures the rate or flatness of skill growth to trigger automated intervention.
- 🔲 Agent intelligence delta measurement — the system must prove it is smarter than 30 batches ago: today, skill counts grow and `needs_human` is tracked, but there is no metric that captures whether the agents are actually making better decisions over time. A proxy: compare the `needs_human` rate and `time_to_merge_avg_min` from the first 10 batches after each major learn session against the 10 batches before it. If neither improves after 3 consecutive learn sessions, it is evidence that the learning is not transferring to agent decisions. SM §4b must compute this `intelligence_delta` score every 10 batches (after each learn session) and write it to `metrics.md`. PM §5 must flag when `intelligence_delta` is neutral for 2 consecutive learn cycles — a `kind/chore priority/high` issue must be opened: "Skills growing but agent decisions not improving — review skill applicability and ENG skill-load discipline." ⚠️ Inferred from self-improvement lens: agents are not measurably smarter; the system claims self-improvement but has no metric that confirms the claim.
- 🔲 Learn session skill-extraction verification: SM §4c learn-cadence enforcement opens a learn issue when PROVENANCE.md is >14 days stale — but it does not verify the learn PR was merged and a new skill file was actually created in `agents/skills/`. SM §4c must: (1) after opening a learn issue, record the issue number as `pending_learn_issue: N` in `state.json`; (2) every SM cycle, check if that issue is closed with a merged PR; (3) if closed: verify `agents/skills/` has a file newer than the issue creation date (via `git log --since` on the skills directory); (4) if closed but no new skill file found: open a `kind/bug priority/medium` issue "learn session closed but no new skill extracted — PROVENANCE.md updated without adding a skill file." Currently the learn cadence loop fires but has no feedback: a learn issue can be closed without producing any learnable artifact, and the system moves on silently. ⚠️ Inferred from self-improvement lens: /otherness.learn runs rarely; when it does run, there is no mechanism confirming the learning was captured as a reusable skill.
- 🔲 Health signal GREEN/AMBER/RED requires observable proof, not inference: the current health signal is computed from `prs_merged`, `needs_human`, and vision alignment — but all of these are written BY the SM phase itself (same session that computes the signal). This creates a confirmation loop: SM writes metrics, SM reads metrics, SM declares GREEN. A truly honest health signal requires at least one piece of external evidence — something the SM did NOT write. The simplest external evidence: the `_state` branch diff shows commits from more than one session in the last 12 hours. If `_state` shows only one session's commits (the current session), the health signal must be marked `AMBER (single-session only)` — the system is not demonstrating continuity of execution, only that one session ran. This is a weak but falsifiable honesty gate: it forces the health signal to acknowledge when it cannot verify its own continuity. ⚠️ Inferred from honesty lens: the SM health signal says GREEN but there is no independent verification; a system that can only confirm its own outputs is not honest about its state.
- 🔲 Metrics schema must be validated against agent instruction claims before each SM cycle: design docs mark multiple ✅ Present items claiming SM §4b "writes X column to metrics.md" — but the only way to verify these claims is to count the columns in the actual metrics.md data rows. SM §4a must add a one-time per-session schema validation step: read the header row of `docs/aide/metrics.md`, read the last data row, compare column counts. If they differ: write the discrepancy to `state.json` as `metrics_schema_drift: true` and include it in the health comment as `⚠️ metrics.md column count mismatch (header: N, data: M)`. This is the minimum honesty gate: the system must expose when its own data structures disagree with its claims. A GREEN health signal that rests on schema-inconsistent metrics is not a honest signal. ⚠️ Inferred from honesty lens: design docs claim metrics columns are being written but no automated check verifies the data rows match the schema — the implementation may be incomplete and the system has no mechanism to detect this.
- 🔲 `needs_human` rate must distinguish "human needed for design decision" from "human needed for ops failure": the `needs_human` metric conflates two completely different signal types. A `[NEEDS HUMAN: critical-tier-change]` post is a deliberate safety gate — it correctly requires human judgment. A `[NEEDS HUMAN: ci-red-for-48h]` post is an operational failure — the system could not recover from a broken build. Both increment the same `needs_human` counter, but they mean opposite things: the first is the system working as intended, the second is the system failing. SM §4b must split `needs_human` into two columns: `needs_human_design` (issues with titles matching `critical-tier|design-decision|vision-fork`) and `needs_human_ops` (all others). PM §5 stagnation check must flag when `needs_human_ops > 0` for 2 consecutive batches (operations are failing) while ignoring `needs_human_design` as expected overhead. Without this split, a well-behaved system that correctly escalates design decisions looks identical in the metrics to a system that is failing operationally — both report elevated `needs_human` and trigger the same regression detection. ⚠️ Inferred from honesty lens: the loop is not honest enough because the health signal cannot distinguish deliberate design escalations from operational failures.
- 🔲 Batch completion must be verified by an external check, not self-reported: every batch completes with SM §4f writing a health comment and updating `_state`. But the SM phase could fail mid-execution (LLM timeout, GitHub API rate limit, runner OOM) and exit without writing either artifact. The next session then reads a stale `_state` and either re-runs work or skips it. There is no external mechanism that confirms "SM §4f ran to completion." The fix: add a post-batch verification step in `standalone.md` (outside SM's own code path) that reads `_state` and verifies: (1) `batch_number` was incremented since last read, (2) `last_sm_run_at` timestamp is within 10 minutes of current time. If either check fails: write `batch_incomplete: true` to `_state` and post `[NEEDS HUMAN: incomplete-batch]`. This is a watchdog outside the component being watched — the only kind of verification that can catch that component's own failure. ⚠️ Inferred from honesty lens: the SM health signal says GREEN but if SM itself failed mid-run, the system has no way to detect or surface this.

- 🔲 Intelligence delta measurement requires a before/after comparison window, not a single-point computation: the `intelligence_delta` item above specifies comparing the 10 batches before vs. 10 batches after each learn session. But this comparison requires storing the "before" snapshot at learn-session creation time — not at evaluation time 10 batches later. SM §4c must, at the moment it opens a learn issue: (1) read the current 5-batch rolling averages for `needs_human`, `time_to_merge_avg_min`, and `meaningful_prs` from `metrics.md`; (2) write these as `pre_learn_metrics: {needs_human_avg_5b, ttm_avg_5b, meaningful_prs_avg_5b}` to `state.json`; (3) note the batch number as `pre_learn_batch`. Without this snapshot, a learn session that runs at batch 95 and is evaluated at batch 105 cannot compare "before" vs. "after" — it can only read the current trailing 10 batches, which mixes pre-learn and post-learn data and produces a meaningless delta. The intelligence delta metric is specifiable but not implementable until the "before" snapshot is written at the right moment. The absence of this snapshot is the implementation gap that makes the entire intelligence-delta measurement unworkable, regardless of how SM §4b computes the score. ⚠️ Inferred from self-improvement lens: the agents are not measurably smarter than two weeks ago; the intelligence_delta metric as specified in this doc is not computable without a pre-learn snapshot stored at claim time; this is the specific implementation gap that prevents the metric from being meaningful.

- 🔲 Self-update failure must be detected and reported — a session running stale agent files is not improving the right loop: every session begins with `git -C ~/.otherness pull --quiet 2>/dev/null || true`. The `|| true` means a failed pull (network error, detached HEAD, permission denied, conflicting local changes) is silently ignored. The session then runs with whatever version of agents happen to be on disk — potentially days or weeks behind `main`. All improvements shipped via recent PRs are absent. The self-update is the single most important step for ensuring improvements to the agent loop actually reach running sessions — and it is the only step that deliberately swallows its own failure. `standalone.md §0 SELF-UPDATE` must: (1) capture the git pull exit code; (2) if non-zero: read the current commit hash before and after the attempt (`git -C ~/.otherness rev-parse HEAD`); (3) if pre-hash == post-hash AND pull failed: write `self_update_failed: true` and `self_update_failed_at: <date>` to `_state` and include a one-line note in the SM health comment: "⚠️ Self-update failed this session — running on stale agents (hash: <pre-hash>)"; (4) if `self_update_failed` has been true for 3 consecutive sessions: open a `[NEEDS HUMAN: self-update-stalled]` issue. Currently the self-update failure mode is invisible: sessions that run on stale agents produce the same outputs as sessions on current agents — there is no way for the operator to distinguish them without manually checking the agent file timestamps. A system that claims to self-improve must know when its improvement mechanism is broken. ⚠️ Inferred from self-improvement lens: the self-improvement loop depends on git pull succeeding at session start; when it fails silently, all subsequent improvements shipped to `main` are absent from every running session; this is the highest-impact single-point failure in the self-improvement chain, and it is currently undetected.

- 🔲 Design doc `✅ Present` claims must be verified against actual agent instruction content before each SM health report: design docs use `✅ Present` to assert that a feature is implemented. But the implementation claim is written by the same session that ships the PR — there is no subsequent check that the instruction actually exists in the agent file and is correctly formatted. Multiple ✅ Present items in this doc reference "SM §4b writes X column to metrics.md" — but the actual metrics.md data rows show those columns are absent (fewer columns than the schema header). The pattern: an ENG session adds a ✅ Present line, SM marks the item shipped, but the agent instruction was either omitted, written in the wrong section, or overridden by a later PR. SM §4a must run a spot-check every 10 batches: for each ✅ Present item in `docs/design/33-stage-4-self-improvement-metrics.md` that names a specific SM §4b column (e.g. "writes `vision_prs` column"), verify that the column header exists in `docs/aide/metrics.md` AND that the last data row has the correct column count. Any mismatch: flag `implementation_claim_unverified: [item text[:50]]` in `state.json` and include it in the next health comment. This is the minimum honesty gate for a doc about metrics — if the doc that tracks self-improvement cannot verify its own claimed implementations, the entire self-improvement narrative is based on unverified assertions. ⚠️ Inferred from honesty lens: the loop is not honest enough; metrics are collected but the schema-execution gap means key columns claimed as ✅ Present may not be written; without a verification step, the system's health signal rests on unverified implementation claims.

- 🔲 `loop_honesty_score < 70` must produce a COORD behavioral change — not just an AMBER signal: doc 45 specifies a `loop_honesty_score` (0–100) computed by PM §5 every 10 batches and included in the health comment. 45.1 states that `score < 70` → health AMBER. But AMBER is an information signal, not a behavioral constraint on the next session. A human reading AMBER who does nothing still has COORD claiming whatever is next in the queue — the honesty gap continues while the queue processes. COORD §1b-preflight must read `loop_honesty_score` from `state.json` and, when `score < 70`: (1) set `HONESTY_RECOVERY_MODE=true`; (2) in `HONESTY_RECOVERY_MODE`, COORD must claim only items from the honesty-recovering category: items from docs 45, 33, 35 that address the specific honesty component that scored lowest; (3) if no such items exist in the queue: COORD must generate one before claiming anything else; (4) after 3 consecutive batches in recovery mode with the score still < 70: escalate to `[NEEDS HUMAN: honesty-recovery-stalled]`. Without this behavioral change, the honesty score is a dashboard metric that observes but does not alter the loop's direction — it is precisely the "metrics collected but not acted on" failure mode the pressure context names. A score below the threshold must translate into a concrete change in what COORD does next, not just a color on a table. ⚠️ Inferred from honesty lens: metrics are being collected but not acted on; the loop_honesty_score is defined in doc 45 but produces no behavioral consequence in COORD; the gap between "COORD reads honesty score" and "COORD adjusts its claims based on the score" is the specific closure the pressure context demands.

- 🔲 Metric-to-action registry — each tracked metric must have an explicit named owner and response action for each regression type: `docs/aide/metrics.md` tracks 10+ columns. SM §4b detects regressions and opens issues. But the mapping between "this metric regressed" and "this specific agent does this specific action" is scattered across multiple phase files and has no single authoritative reference. A developer adding a new metric must read all phase files to determine where to add the regression handler. When a metric regresses unexpectedly, the operator must read all phase files to understand what action the system is supposed to take. `docs/design/33-stage-4-self-improvement-metrics.md` must add a **Metric Registry** section: a table with columns `metric_name | owner_phase | regression_trigger | response_action | escalation_if_unresolved`. Example row: `needs_human_ops | SM §4b | >0 for 2 consecutive batches | open kind/chore priority/high: "ops escalation spike" | [NEEDS HUMAN: ops-blocked] after 3 batches`. Every metric in `metrics.md` must have one row. SM §4b must validate at each SM cycle that all metrics in `metrics.md` have a corresponding registry entry — if a new metric column has no registry row, SM must open a `kind/chore priority/medium` issue: "Unregistered metric: `<column_name>` has no owner or regression handler in the metric registry." Without this registry, the metric system is a collection of observed values with no defined obligations — metrics are collected but their governance is implicit, scattered, and frequently unimplemented. The pressure context names "metrics collected but not acted on" as a live problem; the registry is the concrete structural fix. ⚠️ Inferred from honesty lens: each metric must have a named owner action when it regresses; currently no single artifact maps metric names to their obligated responses; this gap makes the metric governance unverifiable and difficult to audit.

- 🔲 Agent output quality measurement on standardized task types — concrete baseline comparison for "are agents smarter?": `intelligence_delta` (above) measures improvement via `needs_human` and `time_to_merge` proxies — but these are indirect measures. A direct measure: give each agent a standardized task every 20 batches and compare the output quality to a baseline established at batch 0. For ENG: implement a fixed, non-evolving feature request (e.g. "add a `--dry-run` flag to `scripts/validate.sh`") and measure: (1) number of implementation attempts before CI passes, (2) QA approval without change requests, (3) lines of code written vs. minimum required. For COORD: given a fixed queue of 10 items with mixed priority/size labels, observe which item is claimed first and whether it matches the optimal sort key. These are repeatable tasks — the same task each time — so improvement is directly observable. SM §4c must generate a "standardized task probe" issue every 20 batches: a fixed-spec issue labeled `kind/probe priority/high` that is always the same task. After the probe PR merges: SM §4b records `probe_attempts`, `probe_qa_pass_first_try: bool`, `probe_net_lines` in `metrics.md`. PM §5 computes `probe_quality_trend`: is each probe better than the last? If `probe_quality_trend` is flat or declining for 3 probes: PM must open `kind/chore priority/high`: "Agent output quality not improving: standardized probe results flat for 3 cycles." Without this measurement, "are agents smarter?" is answered by inference (skills count, needs_human rate). The probe provides a direct, falsifiable comparison across time. ⚠️ Inferred from self-improvement lens: the agents are not measurably smarter than two weeks ago because all current measurements are indirect proxies; a standardized repeatable task creates a direct before/after comparison that cannot be gamed by metric manipulation.
