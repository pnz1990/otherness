# 32: Stage 3 — Onboarding Quality

> Status: Complete | Created: 2026-04-20

---

## What this does

Makes `/otherness.onboard` reliably produce a complete `docs/aide/` set for any
standard project without requiring manual editing. The acceptance criterion is:
after running `/otherness.onboard`, `/otherness.run` starts autonomously without
any human corrections to the generated files.

## Future (🔲)
- 🔲 SM §4f must update `docs/aide/progress.md` every batch with accurate state: `docs/aide/progress.md` currently says "Batch 22 (2026-04-17)" — the actual batch count is now 93+. The document is a lie that a human will find and distrust. SM §4f must: (a) read the current batch count from `docs/aide/metrics.md` (count rows), (b) read the most recent health signal and last-shipped PR title from state.json, (c) rewrite the "Current State" section of `docs/aide/progress.md` with accurate batch number, date, health signal, last-shipped PR, and queue depth. This is the same gap identified in `docs/design/06-command-surface.md` — but the specific symptom (progress.md frozen at Batch 22 while reality is Batch 93) makes the priority concrete. A human looking at the repo today sees stale progress and cannot tell if the system is alive. ⚠️ Inferred from visibility lens: docs/aide/progress.md is 71 batches behind reality; the system's self-reported state is wrong.
- 🔲 `/otherness.onboard` must generate a project-specific vision pressure context: when a new project is onboarded, the scheduled workflow is created with the generic otherness pressure prompt (the one in this file). But a new project (e.g. a React dashboard app) has completely different gaps than otherness itself. The first 3–5 batches after onboarding will be driven by the otherness self-improvement pressure, not by the actual project's needs. `/otherness.onboard` must: (1) read `docs/aide/vision.md` and the project codebase, (2) synthesise a project-specific "Context for this vision scan:" block addressing the project's real gaps, (3) write it into the scheduled workflow file before committing. Without this, every new project starts with misdirected pressure and wastes its first batches on the wrong work. ⚠️ Inferred from onboarding lens: new project onboarded today would get otherness-specific pressure prompts irrelevant to its own codebase.
- 🔲 Onboarding generates `docs/design/` stubs from real codebase analysis: `/otherness.onboard` currently creates `docs/aide/` files but does NOT create `docs/design/` stubs. The result: a newly onboarded project's COORD finds no `🔲 Future` items in `docs/design/`, the queue refusal guard fires immediately, and the session falls back to autonomous vision synthesis — generating lower-quality machine-inferred items rather than human-quality design docs. `/otherness.onboard` must produce at least 3 `docs/design/` stubs with real `🔲 Future` items derived from codebase analysis, covering the most important improvement areas visible in the code. This gives the first batch a meaningful queue without requiring human authorship of design docs first. ⚠️ Inferred from onboarding lens: onboarding produces docs/aide/ but not docs/design/; first-batch queue will be machine-generated noise, not design-backed work.
- 🔲 `/otherness.onboard` must seed the first-batch GitHub issue queue automatically: after generating `docs/aide/` and `docs/design/` stubs, `/otherness.onboard` must run the queue-generation step inline — creating 3–5 GitHub issues directly from the `🔲 Future` items it just wrote. Without this, the first `/otherness.run` session starts with an empty queue, triggers COORD §1c queue-gen from scratch, burns 30% of its session budget on overhead, and may generate lower-quality items than what the onboarding agent already knows. The onboarding agent has just read the codebase — it is the highest-quality source of initial items. It must write those items as GitHub issues before exiting. A new project added today should have its first batch of real work waiting before the human even closes their terminal. ⚠️ Inferred from onboarding lens: new project added today requires significant human intervention; first session wastes budget generating what onboarding already knows.
- 🔲 SM must auto-detect and report first-batch success for newly onboarded projects: the acceptance criterion in this doc is "first batch ships ≥1 PR with zero [NEEDS HUMAN] posts" — but there is no mechanism that (a) detects when a project is on its first batch, or (b) verifies and reports whether the criterion was met. SM §4b must: (1) detect `batch_count == 1` (first row being written to `metrics.md`); (2) after the session completes, check whether ≥1 PR was merged AND 0 `[NEEDS HUMAN]` issues were opened; (3) post to the report issue: "🎉 First batch: PASS — 1 PR shipped, 0 [NEEDS HUMAN]" or "⚠️ First batch: FAIL — [diagnosis]". Currently a newly onboarded project's first batch can fail silently (0 PRs, 1 stale [NEEDS HUMAN]) and the operator has no automated signal that onboarding was incomplete. The acceptance criterion is human-verified only; it must become machine-verified. ⚠️ Inferred from onboarding lens: a new project added today would still require significant human intervention — without first-batch auto-reporting, the operator cannot tell if the onboarding succeeded without manually checking.
- 🔲 Onboarding setup verification command: `/otherness.setup` must perform a final validation step that confirms the five first-run prerequisites (report_issue integer, autonomous_mode set, GitHub labels present, AGENTS.md REPORT_ISSUE valid, scheduled workflow present and enabled) and outputs a clear PASS/FAIL for each. Currently `scripts/check-onboarding.sh` covers 4 of these — but it must be runnable by a human mid-onboarding to diagnose failures before the first session, not just after `/otherness.onboard` exits. The setup guide (`onboarding-new-project.md`, `onboarding-existing-project.md`) must include a "Run the verification gate" step referencing the command. Without an operator-runnable verification command that outputs human-readable PASS/FAIL, a new user has no self-service diagnostic path when onboarding stalls. ⚠️ Inferred from onboarding lens: setup guide is incomplete; no single command a new user can run to confirm all prerequisites before starting the autonomous loop.
- 🔲 Cross-project monitor detects "dark projects" — onboarded but never ran successfully: a project can be fully onboarded (AGENTS.md, docs/aide/, secrets set, scheduled workflow deployed) and yet never produce a first successful batch — credentials expired before first run, repo was archived, the workflow was created but never enabled, or the first session failed silently with no PR. From the `monitor.projects` list in `otherness-config.yaml`, these projects are invisible — the cross-agent monitor only checks `_state` activity, but a dark project may have no `_state` branch at all (never ran). PM §5 must: (1) for each project in `monitor.projects`, check whether a `_state` branch exists; (2) if no `_state` branch: check whether a scheduled workflow file exists in `.github/workflows/` on `main`; (3) if workflow exists but `_state` is absent: the project was onboarded but never ran — open a `[NEEDS HUMAN: dark-project]` issue: "Project <repo> appears onboarded (workflow present) but has no _state branch — first session never completed. Check workflow permissions and secrets."; (4) do NOT re-open the issue if one is already open. Without this check, a dark project can sit in the monitor list indefinitely with no automated detection. A new project added today could stall silently for weeks with no signal. ⚠️ Inferred from onboarding lens: a new project added today would still require significant human intervention to get running; there is no automated mechanism to detect when a newly onboarded project has never successfully started.
- 🔲 `/otherness.onboard` must prompt the operator with a post-onboarding checklist before closing: the onboarding agent currently generates files and opens a PR, then exits. The operator then needs to: set secrets (`AWS_ROLE_ARN`, `GH_TOKEN`), enable the workflow, trigger the first `workflow_dispatch` run, verify `_state` is created. None of these steps are prompted after the PR merges. `/otherness.onboard` must append a "Post-merge checklist" as a PR comment on the onboarding PR itself, listing each setup step with the exact command (e.g. `gh secret set GH_TOKEN --repo owner/repo`). This comment is the human's task list — they don't need to read any docs. The comment must also include `scripts/check-onboarding.sh` as the final verification command. Without this checklist, the operator must either know these steps from memory or read through onboarding docs — both are failure modes for a first-time user. ⚠️ Inferred from onboarding lens: a new project added today would still require significant human intervention; the onboarding agent does not guide the operator through the post-merge activation steps that are required before the first autonomous session can run.
- 🔲 Onboarding health check must verify the PAT scope matches required permissions: `/otherness.setup` validates that `GH_TOKEN` exists as a secret but does not verify its scopes. A PAT with only `public_repo` scope (common mistake) will fail silently when the agent tries to push to a private repo or create workflow runs. `scripts/check-onboarding.sh` Check 6 must: run `gh auth status --show-token 2>/dev/null | grep -E "scopes:"` and verify both `repo` and `workflow` appear in the scope list. If not: output `FAIL: GH_TOKEN missing required scopes (found: X, need: repo,workflow)`. This is a common onboarding failure that is currently diagnosed only when the first session fails and the operator reads the workflow log. A pre-flight scope check at onboarding time eliminates this class of failure before the agent loop ever starts. ⚠️ Inferred from onboarding lens: the setup guide is incomplete; PAT scope validation is a missing first-run prerequisite check that causes silent first-session failures.
- 🔲 The scheduled workflow must be enabled via `gh workflow enable` as part of onboarding: GitHub creates workflows in a disabled state if the repo was forked or if the workflow file was added without being enabled via the UI. `/otherness.onboard` and `/otherness.setup` must call `gh workflow enable otherness-scheduled.yml --repo owner/repo` as the final step before posting the completion message. Without this call, a freshly onboarded project's scheduled workflow is silently disabled — the cron trigger fires but the run is skipped with "Workflow is disabled" in the Actions UI, producing no `_state` activity and no error that surfaces in the repo. The "dark project" detection (above) would eventually catch this, but the workflow-enable step prevents the problem from occurring at all. ⚠️ Inferred from onboarding lens: a new project added today would require significant human intervention; enabling the scheduled workflow after the PR merges is a manual step that is not currently part of the onboarding procedure.
- 🔲 `otherness-config.yaml` must be validated for completeness at onboarding time: `/otherness.onboard` generates a project's `otherness-config.yaml` from the template — but there is no step that validates the output against the template schema before the onboarding PR is created. Common failures: `report_issue` left as `0` (placeholder not replaced), `schedule.cron` absent (loop never runs), `maqa.agents_path` pointing to a wrong directory. `agents/onboard.md` STEP 7c must add a `config-validation` check: parse the generated `otherness-config.yaml`, verify `report_issue` is a real positive integer, `schedule.cron` is a valid cron expression (not `""` or missing), `maqa.agents_path` expands to a directory that exists. Any failure must abort the onboarding PR creation and post to the operator: "Config validation failed: [items]. Fix these fields before the first session can run." Without this check, malformed configs silently block the first session with cryptic Python errors. ⚠️ Inferred from onboarding lens: a new project onboarded today would produce a misconfigured `otherness-config.yaml` without any validation step to catch placeholder values left over from the template.
- 🔲 Onboarding quality feedback loop — grade each new project's first 5 batches and improve `agents/onboard.md` from the results: the onboarding process produces `docs/aide/` files and a setup PR — but there is no feedback mechanism that grades how well the onboarding actually worked. A project that required 3 manual corrections to `docs/aide/vision.md` before the first session ran cleanly is evidence that `agents/onboard.md` produced inaccurate vision docs. PM §5 must: (1) for each project in `monitor.projects` where `batch_count ≤ 5` (early-stage project), read `[NEEDS HUMAN]` issues opened in that project's first 5 batches and count those attributable to "missing or wrong docs/aide/" content (body mentions `docs/aide/`, `vision.md`, `roadmap.md`, `definition-of-done.md`); (2) for each such project, write a `onboarding_quality_score: N/5` where N = batches completed without a docs-related NEEDS HUMAN; (3) if `onboarding_quality_score < 3/5` for any project: open a `kind/chore priority/high` issue on the otherness repo: "Onboarding quality gap detected on [project]: [N] docs-related NEEDS HUMAN issues in first 5 batches — root cause: [issue titles]. Review `agents/onboard.md` [specific step] that generates [specific file]." Without this feedback loop, `agents/onboard.md` can produce systematically wrong vision docs for every new project and the gap is never surfaced as a fixable defect. The onboarding agent cannot improve itself without a signal from the projects it created. ⚠️ Inferred from onboarding lens: a new project added today would still require significant human intervention to get running; there is no automated mechanism to detect when the onboarding agent produced inaccurate docs and feed that signal back into improving the agent itself.

## Zone 1 — Obligations

**O1 — `/otherness.onboard` generates all required `docs/aide/` files.**
Required: `vision.md`, `roadmap.md`, `definition-of-done.md`. Optional: `progress.md`, `metrics.md`.

**O2 — Generated files are accurate enough to start `/otherness.run` without edits.**
The measure: no `[NEEDS HUMAN]` issues in the first batch after onboarding due to missing
or wrong `docs/aide/` content.

**O3 — `AGENTS.md` template is complete.**
Every required field in the template is populated with accurate project info.
